日期：2026-10-01。本轮按用户要求修改运行代码，反复检查完整业务模块与平台 API 的职责。当前接口与字段清单见 [P1_P2_API_INVENTORY.md](P1_P2_API_INVENTORY.md)，正式业务用法见 [概念 README](../preparation/concepts/README.md)，平台通用契约见 [web_evidence](../../demiflow/docs/web_evidence.md)。

## 1. 结论与适用范围

新 P1→P2 主图已经改用 Dataset 原生搜索、获取、阅读、模型、小批提交与执行接口。通用 I/O、调度、正文处理、材料预算、完整上下文适配、资源生命周期和技术观测已由平台承接。概念身份、原名与等义关系、问题与证据绑定、一次补查、视觉任务、分类和采纳规则仍在业务模块。

这次没有热切旧 collect 的生产消费者，没有改图片下载、QID、公共概念／图片表或其他训练评测流程。旧 collect 的别名漏传及旧部署／消费者迁移仍按 collect TODO 后续处理。新概念流程不依赖那些旧业务执行器。

工程边界和回归通过不等于真实语义质量已通过。本轮真实检索／下载可用；真实 P1 正常交付；正式新图中的两次真实 P2 都被上游 HTTP 408 中断。随后按用户要求独立重放此前成功的“银杏”P2 原始请求，约 92.68 秒得到有效响应（第 5.5 节）；这是模型传输对照成功。随后重放此前失败的“天牛”原始请求，关闭重试后仍在约 125.96 秒超时（第 5.6 节），未完成该概念审定。随后按用户要求把同一原始请求改为 HTTP 流式接收，在约 140.67 秒完整取得符合 schema 的响应（第 5.8 节）；正式业务 pipeline 尚未切换传输方式。失败被完整保留，不能称为“天牛已核验完成”或“适合全量直接放行”。

## 5. 有界真实验证

### 5.1 种子消费者：原生服务、搜索、下载、缓存

通过 Dataset.search_web → fetch_documents 执行查询“银杏天牛”，受管服务只启用 wikisearch 与 wikipedia，使用真实网络和网页对象。冷运行约 7.90 秒，取得一份可解析网页；停止服务后重放约 0.01 秒，不再发搜索／下载请求。

实际返回包含“银杏”等页面，说明技术可用不等于命名歧义已解决或证据相关。这里不添加名称命中硬淘汰，也没有把这些候选当作“银杏天牛”成立的证明。证据在 `live_v2/result.json` 与 `live_v2/replay.json`。

### 5.2 概念消费者：实际 master 来源、“天牛”、指定模型

输入为公共 `datasets/master_concepts.lance@4` 中的一个“天牛”记录，只读访问；所有阶段表与新对象位于隔离目录。模型为用户指定的 `malasci/gpt-6.1-sol`，沿用此前实测 token 档案。P1 最大一次、首次 P2 和后续尝试的额度均显式配置。demiflow 模型客户端没有自动重试；但后续核对网关日志发现 LiteLLM 对每次失败的 P2 自动重试了两次，因此这些额度只限制发往网关的请求数，不限制网关内部的实际尝试次数。此前“没有模型自动重试”的表述没有覆盖完整服务链，现予以纠正。

本轮 P1 正常交付：HTTP 200，耗时 55.797609 秒，finish_reason=stop。实际查询如下；程序保留原名查询，并把 P1 生成查询的不足完整暴露给 P2。

| 天牛 天牛科 Cerambycidae Longhorn beetle カミキリムシ 长角虫 锯树郎 俗名 | no_results。 |

取得两份可读文档，首次选取 38 个完整块、12,000 个材料 tokens，随后进入真实 P2。首次 P2 在约 380.75 秒收到 HTTP 408；流程总耗时约 456.88 秒，结果为 `model_error`、`complete=false`、assessment=null。没有伪造核验结论。相同输入重放约 8.76 秒，复用失败记录，没有再调用模型。

为区分执行衔接与输入规模的影响，保留原日志、复用 P1 和文档，将首轮材料明确改为 4,000 tokens，只额外开放一次新的 P2 请求，关闭补查后的模型调用额度。这是显式的新输入试验，不是隐藏重试。该次 P2 又在约 381.37 秒收到 HTTP 408，总耗时约 390.25 秒。不能据此断定超时原因就是输入长度。后续只读检查已定位到上游 Cloudflare 524 和本机 LiteLLM 两次重试，详见第 5.4 节；上游处理为什么迟迟未返回仍需服务方证据。本轮到此停止新增付费请求。

demiflow 日志合计三次网关请求：一次有成功响应的 P1、两次返回 HTTP 408 的 P2。网关日志表明，两次 P2 分别经历首次尝试加两次重试，共六次路由尝试；供应商更深层是否又重试以及实际计费情况无法从本地日志确认。P1 已知 usage 为 1,907 input tokens、870 output tokens；两次 P2 均没有 usage，消耗未知，不能按零计费。当前没有新得到的有效 P2 审定，因此本轮未完成真实语义质量验收。

原始记录在 `concept_live/config.json`、`result.json`、`assessments.json`、`config_small.json`、`result_small.json` 及原生调用 SQLite。最后另以三个模型节点新增额度均为零运行新代码重放，约 8.81 秒完成，前后调用日志统计完全相同，搜索服务保持停止。验证回执在 `concept_live/final_zero_budget_replay.json`；该回放用于验证恢复与不增加调用，不把失败变成成功。

### 5.3 对后续质量工作的含义

本次代码已经把召回、获取、阅读和审定分开留证，因此可以具体判断哪一层失败。这个例子里原名召回有效，三条较长查询召回为空，文档读取成功，P2 服务请求超时；不能笼统归因于“下载文档不行”。查询语言／长度的效果和模型服务稳定性需要各自验证，后续可据这些记录讨论 P1 prompt 与部署档案；本轮没有借平台迁移擅自修改这些业务策略。

### 5.4 两次 P2 HTTP 408 的实际来源（后续只读排查）

故障链为：概念首轮 `assess_concept` → `Dataset.map_prompt_async` → 本机 LiteLLM `/v1/chat/completions` → `api.malasci.com` 的 Cloudflare → Malasci 源站／中转 → 其调用的模型服务（内部链路不可见）。搜索、获取、正文解析和材料阅读已经完成；约 381 秒是模型 HTTP 调用耗时，不是网页下载耗时，也不是整条 pipeline 的耗时。

| 层次 | 现场证据 | 结论 |
| --- | --- | --- |
| demiflow 客户端 | 两份 response journal 为 HTTP 408，elapsed_s 分别为 380.750205 和 381.370390；`config.timeout_s=600`。 | 是收到 HTTP 错误响应，不是本地 600 秒计时器触发。 |
| 上游边缘代理 | 两份完整错误正文都包含 `Error code: 524`、`origin_response_timeout`、`zone: api.malasci.com`，并说明连接已建立，但源站没有在 120 秒 Proxy Read Timeout 内完成响应。 | 直接触发失败的是上游代理的读取超时。 |
| 本机 LiteLLM | `modelhub/logs/gateway.log` 第 357445、357451、357578 行记录 `LiteLLM Retried: 2 times, LiteLLM Max Retries: 2`。 | 每次 P2 有三次路由尝试。三次尝试叠加足以解释约 381 秒总耗时。120 秒来自错误正文，并非本地配置；没有逐次完整计时，不能将总时间精确拆成 3×120 秒加 21 秒退避。 |
| 错误转换 | 已安装 LiteLLM 的 `exception_mapping_utils.py` 将含 `A timeout occurred` 的异常转为 Timeout；`exceptions.py` 为它设置默认 HTTP 408。 | 本地看到的 408 是上游 524 被转换后的状态。 |
| 当前配置 | 目标模型没有显式重试配置，router_settings 没有覆盖；已安装 Router 从默认值取得两次重试。网关配置另有 `litellm_settings.request_timeout=600`。 | 没有发现本地配置了 381 秒超时；确实遗漏了网关默认重试这一层。 |

缩小材料后的最后一次上游错误时间为 `2026-10-01T09:11:35Z`，Ray ID 为 `a43a54310bb409e7`；同次调用首次尝试的错误时间为 `09:07:22Z`，Ray ID 为 `a43a4e02cfcf09e7`。本机最终在 `09:11:38` 记录 HTTP 408。首次较大材料试验的最终 Ray ID 为 `a43a46db595f8548`。这些标识可供服务方追踪。

补充交叉核对：[Cloudflare 当前官方说明](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/)写的默认 Proxy Read Timeout 为 125 秒，而这两份实际错误正文写 120 秒。因此，现场已经确认的是上游代理读取超时和本机两次重试，不能仅凭错误模板断言该域名当前精确配置值为 120 秒。官方说明也明确，调大 Cloudflare 窗口或改 DNS-only 路由属于域名服务方操作，不受本地 LiteLLM timeout 控制。

两份实际模型请求都使用 `max_tokens=8000`、`temperature=0` 和 JSON object 响应格式，未开启流式响应。4,000 tokens 是检索材料额度，不是完整 prompt 大小；缩小材料没有改变输出协议。输出长度上限并不表示模型一定生成 8,000 tokens。现有证据无法区分供应商排队、推理／生成耗时、内部代理阻塞或其他源站问题，也不能断定是概念内容或参数格式错误。

进一步只读核对历史 `concept_final2_20261001` 原生 SQLite：同一模型的首次 P2 两次均为 HTTP 200，耗时 57.915214／56.328324 秒；补查后的 P2 两次也为 HTTP 200，耗时 66.296442／73.048602 秒，均为 finish_reason=stop。因此“本轮两次 P2 超时”不能扩展成“P2 从未成功”。历史结论仍是身份未核实、出题暂缓；HTTP 成功不等于概念审核通过。

继续核对已保存的完整请求：4,000 是材料额度，本次实际材料为 3,914 tokens；按当前已校准档案计算，完整 P2 输入为 10,959 tokens。较大材料试验的完整输入为 19,196 tokens。两次失败均无服务端 usage，因此这两个数字是本地计数，不能当作供应商实报用量。此前同模型、同 `assess-concept-3`、同 max_tokens=8000／JSON object／temperature=0 的成功首轮 P2，服务实报输入为 24,356 和 24,644 tokens，本地计数与其一致，耗时约 58／56 秒。故现有证据不支持把本轮失败直接归因于输入超过容量或“4,000 tokens 仍然太大”；请求内容、时间和服务状态并未受控，仍需有界对照试验区分。

### 固定前缀与缓存复用检查

按用户补充要求检查了实际消息，而不只看 YAML 中变量的位置。`demiflow.operator_llm.client.request_messages` 先放固定输出 schema 的 system 消息，再放提示词正文的 user 消息。四份模板各有一个末尾的 `payload | json` 动态插槽，前面的说明、例子和字段解释均固定；使用两个不同载荷渲染，确认 system 消息和动态插槽之前的正文分别一致。平台 JSON 渲染按键排序，不受 Python 字典插入顺序影响。

当前已经具备“同一阶段固定前缀、变量置后”的文字布局。不同阶段的 schema 和职责不同，本轮未将四份提示词合成一个大模板，也没有为凑缓存长度增加文字。P2 两轮使用相同模板，但动态输入内部包含变化的回执、阅读目录及轮次，尚未设计不变材料与新增材料的独立分块；仅调整字典插入顺序不能解决这一点。

缓存命中还受实际服务端协议、缓存边界及保留时长影响。OpenAI 当前文档明确说明，共享文本前缀不总等于存在可复用的缓存边界，某些模式需要显式标记固定内容的结束位置。该文档用于提醒核对协议，不能据此推定 `api.malasci.com` 的兼容接口支持同样参数；本次没有盲加缓存参数或改换接口。[官方说明](https://developers.openai.com/api/docs/guides/prompt-caching#gotchas)

读取既有英文六概念试验的 13 条成功响应，P1 六条中三条原始 usage 包含 `prompt_tokens_details.cached_tokens=2816`，对应 `prompt_tokens` 为 3,005、3,000、3,001。这说明该路径在这些历史调用中报告过缓存命中；其余三条 P1 以及七条 P2 没有报告此字段，不能把缺失按零命中处理，也不能推算整批命中率或费用。它们是旧提示词运行回执，不是新版效果验证。

KV/prompt cache 复用输入计算，模型仍执行新的生成；demiflow journal 则可直接复用已经保存的完整响应。后续性能统计应分别记录供应商实际返回的缓存用量、输入输出用量、时延和费用，不把两种复用混作一个命中率。

### 验证结论与限制

概念模块现有测试 36 项通过（109.75 秒），概念相关布局检查 5 项通过、48 项未选（7.56 秒）。之后两处句子进一步明确“P1 只安排核验”和“P2 可以暂缓”，最终版本重新执行关键流程检查，25 项通过（89.31 秒），其中包含首轮、补查、完整请求预算及恢复路径。这些是重叠的回归检查，不能相加宣称独立案例数。本轮没有新增真实模型调用，也没有开展新图像生成、评审或 3,315 概念全批运行。

本轮能确认的是表达、字段契约与执行链路的衔接，以及既有真实载荷的预算兼容情况。自动测试中的模型响应由测试夹具提供，不能据此声称真实模型已经减少误判或补查。后续质量验证应使用未写进提示词的新案例，分别检查事实引用是否支持结论、范围是否保持、任务方向是否满足标准，以及补查是否针对决定性缺口。

仍需保留模型判断的部分包括“这项核心区别是否值得考察”和“这个分类依据能否支持后续概念”。本轮为它们补上具体比较方法、例子及暂缓条件，没有把语义判断伪装成可由固定规则完全判定的分数，也不把提示词中的例子作为白名单。

证据保存在工作区 `_demiflow/concepts_prompt_review_20261001/`：`tasks.before.yaml` 与 `tasks.after.yaml` 为审阅前后快照，`verification.json` 记录散列、契约比较、前缀检查、历史缓存回执和最终计量，`verify_prompts.py` 是只读复核脚本，`pytest.log`、`layout_tests.log` 和 `final_regression.log` 保存工程验证。临时材料不构成新的业务入口。
