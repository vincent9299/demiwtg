## 2. 当前主线

两条业务 pipeline、五个业务 prompt 的职责保持：

1. 概念整理：P1 核验问题与取证计划 → 程序取证 → P2 身份/范围/核心事实/视觉出题潜力。首次建树由 P4 基于审定结果提出新树，采纳树版本后由 P3 挂载；后续 P4 按批次处理修树需求。P1–P4 是职责编号，不表示首次建树必须按编号顺序执行。
2. 正式出题：P5 沿用已有 T2I V2，在实际需要出题时调用。

当前先讨论、完善搜索取证及 P2 的交接，再推进视觉树。没有额外粗筛/独立精筛节点，不重新引入模糊的“规则处理简单项，模型处理难项”分流。

P1 结合输入材料和“你掌握的相关知识”提出核验项；两者都可能出错。没有明显疑点时可写待核断言，不强行制造问题。第一版统一取证，P2 根据实际取得的材料审定，不能把模型知识、旧分类或一次搜索命中冒充已核证据。无检索模式已按用户最新决定移到后续需求，见第 3.7 节。

本次概念整理模型按用户 2026-10-01 指定使用 **`malasci/gpt-6.1-sol`**，当前 P1、P2 及补查后的 P2 按此选择规划。后续概念整理节点默认沿用本次指定，若需另配在对应节点讨论时明确。此处记录运行选择，未修改现有代码默认值、未发起调用；路由实际可用性、上下文与输出限额仍需在执行准备时核对，不能仅凭模型名称推定。

## 3. 第一版材料路线：先搜索，不接历史正文

第一版采用：P1 查询计划 → 网页搜索 → 获取目标正文 → 带来源与状态交给 P2。2026-10-01 用户讨论无检索模式后明确“好，先不加入”；第一版不增加关闭检索的分支，不以检索失败触发模型知识兜底通过。

- 原名、别名、QID、旧分类等可以作为带来源的待核线索；实际未提供的字段不得假定存在。
- 暂不接入历史文档正文，不先全量清洗旧文档库。样本存在问题不代表已判定整库不可用。
- 搜索摘要用于候选发现，不自动升级成网页正文证据。
- 获取、解析、截断和技术失败明确记录。网页是否相关、可信、充分由 P2 审定。
- 本轮不附带下载网页内嵌图片，不启动图片审核或生成，不自动无限补查。
- 小规模技术与协议验证和最终全量范围是两件事；若讨论决定做前者，仍不能将其报告为 3,315 条已完成。
- 以后接入已有文档时，只先标准化关联、格式/章节读取、版本和交付结构；与网页材料共用审定，不要求提前证明每篇历史文档可靠。

### 3.1 已确认的取证与补查思路（待实现）

用户认可 P1 → 程序取证 → P2，并在讨论补查停止条件后确认“思路 ok”。以下记录已确认的方向；具体字段、预算和验收案例仍待细化，不代表代码已经支持。

- P1 交付候选解释、核验问题和查询计划；程序执行及去重、复用后仍保留概念—问题—查询—材料的关联。查询命中不是问题已被证明。
- 程序核对计划结构、执行搜索、获取与解析材料并记录预算和失败；P2 判断来源相关性、可靠性和证据是否充分。不新增独立的资料审核模型，不按规则判断语义难易。
- 正文保留来源、获取时间、快照和实际交付范围。长文不能一律截取开头冒充充分阅读；目录、片段与未读部分明确区分，补读方式纳入交接协议。不新增模型摘要节点。
- **第一版默认最多一轮语义补查。** P2 根据实际材料提出具体缺口、关联问题，以及补充查询或已知章节的读取请求；程序在预算内执行，再调用同一个 P2 审定，保留前后记录。一轮可以包含多个有上限的查询或补读，不等于只能访问一个网页。
- 无补查时通常为一次 P1、一次 P2；有补查时多一次 P2。网络等技术失败的重试与语义补查分别计数，都受各自及总请求预算约束，不能通过重试绕过上限。
- 部分网页失败不直接阻止整个概念进入 P2；成功材料与失败记录一起交付。全部请求因技术故障失败时保留技术未完成；正常搜索无结果只能说明本次未找到，不能据此断言概念不存在。
- 一轮补查后证据仍不足、指代不清或来源冲突，记为**核验未决**。记录已确认内容、具体缺口和继续核验需要的资料；需要原始上下文的问题不能靠无限搜索解决。以后有新资料时可以再次核验，当前运行不自动循环。

阅读呈现需区分以下情况，具体 schema 待定，不把它们强行放进同一个状态字段：

| 情况 | 含义 |
| --- | --- |
| 未开始核验 | 尚未执行核验流程 |
| 技术未完成 | 请求、解析、模型等失败，未获得本轮要求的有效交付 |
| 核验未决 | 已有有效审定，但现有材料不足以明确指代或范围 |
| 身份已明确 | 本轮证据支持明确的对象和范围；不代表视觉任务已可用或经过独立复核 |

身份、核心事实和视觉任务分别交付。身份明确但视觉事实不足的概念可保留身份结论并参与建树，出题暂缓；明确是科、属或通称也可以成立，不强行升级到种。身份仍有歧义的记录保留待核，暂不作为身份明确的概念参与建树。原有范围变化需显式处理的约束保持。

工程执行完成与核验结论分开统计：已获得有效“未决”判断可以表示该项本轮审定执行结束；必需步骤的技术失败仍是未完成。全批跑完不能写成全部核验通过，也不能把未决或技术失败从输入分母中删除。

### 3.2 已确认的 P2 交接结构（2026-10-01，待实现）

用户确认 P2 交接思路后要求继续讨论。以下是已定业务结构，具体 schema 和程序校验仍待实现；概念核心内容与视觉应用的当前设计方向见第 3.3 节。

- 输入包括原概念及带来源的线索、P1 候选与问题计划、实际材料及失败/未读记录、当前轮次和剩余预算。补查后的 P2 还收到首次判断、补查请求和执行结果；首次判断可被新证据推翻。
- 每次输出三部分：**逐问题核验结果、当前概念结论、可执行的补查请求**。
- 逐问题说明编号、已回答/仍未决/不适用、具体回答、已读原文位置和缺口。不适用必须解释；允许否定候选解释，也允许明确补入 P1 遗漏的问题。取得候选对象资料不等于证明原名对应它。
- 当前结论保留能确认的含义、类型、范围、限定及原名与规范名关系。不能按回答问题的数量或比例自动判定成立；P2 说明每个关键缺口影响哪项结论。技术有效性检查不代替证据支持性的判断。
- 补查请求说明关联问题、具体缺口和可执行查询，或已取得文档的明确章节。需要原始上下文时单独记录，不能把这种缺口转成无目的搜索，也不强制用完补查额度。
- 程序对有效且预算内的请求执行一轮补查，再调用 P2；无需补查或额度用完时保存本轮有效结论，允许未决。模型失败、协议无效、引用不存在等记技术未完成，不能转成业务否决。各轮保留可追溯记录。

### 3.3 核心内容与视觉应用的当前方向（2026-10-01，待验证）

针对用户保留的疑问，已对照现有 T2I 出题 prompt 讨论其应用方式。用户表示“懂了，看似没什么问题”，因此先按以下方向收敛；这不是实际质量验收，也未授权启动运行。

- 将“概念是什么 → 核心内容是什么 → 如何在图像中呈现和判断”贯穿 P1、取证及 P2。P1 同时提出身份问题与适用于当前概念的核心内容问题，让问题实际影响查询、材料选择与补查，而非只在末尾增加视觉描述。特征/结构、状态、机制、过程、关系、规则是发现内容的角度，不要求逐项覆盖。
- P2 对保留的核心内容说明具体事实及依据、与概念核心的关系、适用条件、合法变化、可考虑的呈现与观察方式，以及图像无法确认的边界。事实的来源依据与模型提出的视觉设计判断分开，不把设计推论伪装成来源结论；没有图片时不声称实际观察过。
- 用一个自然、简短的任务方向检验核心内容能否被实际应用：说明必要展示条件、可观察的实质正确/错误差异和合法变化。P2 不写完整题目，P5 仍按现有出题质量标准审查具体题目；不以冷门、复杂、独有或视觉细节数量代替价值判断。
- 在 P2 的“当前概念结论”中分别交付身份是否明确、核心内容核实到什么程度、当前是否有可靠视觉任务方向。核心内容或视觉方向的证据缺口可以触发既定的一轮补查；某一任务方向暂缓不等于概念不存在，也不强制穷尽可能方向。
- 建树使用身份、范围及支持分类边界的稳定特征和结构；任务草案仅作应用示例，不反向改窄概念。出题使用已审定的核心内容、条件和候选方向，并重新检查具体题目。原名关系与范围变化约束保持。
- 不增加模型环节，不恢复额外粗筛或精筛。后续案例应验证它们是否真正改变提问、取得的材料和业务结论，不能仅检查输出字段存在。

### 3.4 已确认的业务与 demiflow 边界（2026-10-01，待实现）

用户确认该边界符合预期。按能力是否依赖具体业务目标划分职责，不按“代码还是模型”划分；具体接口、默认策略及验收仍待落地。

- demiflow 提供搜索执行、获取、正文提取、元数据/结构保留、分块与定位、通用检索、快照与哈希、技术状态、预算执行、缓存及存储机制。它交付可追溯材料，不宣告某材料可靠、某概念成立或某核验问题已经解决。
- 业务 pipeline 维护 P1/P2 prompt、概念及问题关联、查询计划、候选选择与材料使用策略、提取配置、预算取值、补查范围、审定和完成口径。业务表字段、路径与允许修改的列由消费者明确，不能藏进通用获取算子。
- 采集候选选择回答“值得获取什么”，正文提取回答“页面中哪些是主体内容”，P2 证据审定回答“具体内容是否支持当前问题”。三个职责均保留，别名漏传不能推导为无需筛选。
- 通用正文提取按调用方配置去除导航、页脚、广告等附属区域并保留原始快照；标题/作者/日期作为来源信息，章节标题、表头和图注保持结构。业务选择提取方式和阅读范围；提取成功不等于内容可靠。
- 获取失败、空正文、已识别访问拦截等由平台返回具体技术状态；业务决定重试、替换候选、补查或技术未完成。可检测的重复/编码异常等是技术信号，语义上的拼接、胡编或不相关由 P2 判断，不将可疑信号自动当作概念错误。
- 电商/厂家来源的采用规则属于业务；平台不硬编码“电商全部淘汰”。规格表、结构说明是否对当前型号及问题有效，由 P2 判断。通用排序和过滤机制可以复用，旧名称分数与阈值不能成为所有消费者的强制策略。
- 从种子开始采集、概念取证及后续训练准备可复用同一组通用能力，各自维护资料用途和采纳标准。当前已有 search/fetch/crawl 基础不等于统一材料与状态协议已经完成。

### 3.5 已确认的通用交接协议方向（2026-10-01，待实现）

用户确认以搜索、获取与解析、读取三类操作交接；这是能力与结果协议，不是新增三条业务 pipeline。具体字段名和 API 在实现时按现有能力整理。

- 搜索接收查询、语言、来源和数量上限，返回实际查询及时间、候选 URL/标题/摘要/排名，以及成功、正常无结果或失败原因。概念—问题—查询关系由业务保留；共享查询不得丢失多方关联。
- 获取与解析接收业务选择的候选、提取配置和预算，返回原始及最终 URL、时间、原始快照与哈希、来源元数据、正文结构和位置、获取/解析状态，以及解析器版本与配置。获取成功和解析成功分别记录；同 URL 内容变化形成新材料版本。
- 读取接收固定材料引用、全文/章节/检索要求及阅读预算，返回实际原文块、位置、材料版本、全文或选段标记、未提供范围及选择/预算信息。不生成摘要或改写原文。

- 补读已有章节使用已保存快照；新搜索或获取占补查预算。失败、弃用、未决分别保留，按此前约定恢复或停止。材料复用与模型结论复用分别核对，不能只凭概念名或 URL 复用旧结论。
- 验收关注问题关联、原文保全、引用定位、失败恢复，以及恢复时哪些工作重做。协议已讨论确认，不代表代码、真实模型效果或生产运行已经验收。

| 项目 | 首版默认上限 |
| --- | --- |
| 每概念首轮查询 | 4 个，包含原名查询 |
| 每查询候选 | 前 5 个不同 URL |
| 每查询正文 | 在候选范围内最多取得 2 份技术可读正文 |
| 语义补查 | 最多 1 轮 |

- P2 在一轮补查内可请求读取已有章节/原文块、获取已知未下载候选或发起针对性新查询。不强制先读完已有资料再换来源；补查后保留原材料、新材料及实际失败记录。
- 计划执行完但证据不足可交付核验未决；预算停止时说明未读范围，不声称穷尽来源。必需步骤因技术故障未完成则保持技术未完成。某项结论已获充分依据时可保留，不因任一候选失败而抹去结论或失败记录。
- 验收以实际提供给 P2 的材料与原始正文作对照，检查关键限定/例外、跨语言名称关联、核心内容问题的材料覆盖、广告/标题等误用、补查对缺口的解决程度及第二次 P2 的增益；不只检查字段和技术成功率。

### 3.8 概念粒度的流式执行与各节点并发（2026-10-01 已确认方向，待实现）

用户明确希望采用“取、处理、推”的流式模式：P1 可同时处理多个概念，后续节点也应能独立设置并发，必要时算子内部的处理亦可单独控制。上一轮讨论中的“模型全流程合计 4、搜索获取合计 4”只是尚未确认的建议，不能替代各节点的独立配置；具体并发数和共享服务限额继续讨论。

用户随后明确选择不跨粒度，按“概念行主线、节点内部有界并发”的方案继续设计。本轮 P1—取证—P2 主线始终一行一个原始概念身份；查询、候选、网页等保留为该行关联的子任务和材料引用。主线不通过展开查询/网页行再跨行归并来完成取证，不将通用跨粒度流式归并引擎作为本轮前置工作。该选择不禁止平台按查询、URL 留存细粒度执行记录，也不改变 P4 首次建树所需的批次范围。

- 概念审核链以逐概念推进为目标：某概念 P1 完成即可进入取证，该概念本轮取证任务收齐终态并组装输入后即可进入 P2，不等待全部 3,315 个概念完成上一阶段。补查只等待该概念的补查任务，不阻塞其他概念。
- P1、搜索、网页获取、解析/阅读、P2 等有并发需求的执行节点分别配置并发及有界输入队列。节点并发限制正在处理的任务数，队列深度限制等待任务数；下游队列满时上游等待，避免无限积压。正文及快照尽量通过固定引用传递；队列有界不等于整个进程内存已有硬上限。
- 一个概念可包含多个查询、一个查询可关联多个页面。各概念节点内部调用 demiflow 的通用异步搜索、获取与读取操作，有界并发并收齐本行子任务；内部不启动子 Dataset，不另行扫描全表或包住整条业务流程。必须明确每条输入的局部并发上限和共享在途请求上限，不能将“并发概念数 × 每概念并发请求数”误报成后者；P1、P2 及补查再审定保持为主线上可见的模型节点。
- 搜索、获取与解析、读取材料分别保留为主线上可见的概念节点，输入输出仍是概念行。平台操作的基本单位可以是单个查询、URL 或读取请求，接口不依赖“概念审核”的字段与判断；业务节点负责当前概念的问题关联、候选策略和预算值。内部并发发起前预留额度，不先超额获取再丢弃结果。
- 同一服务的总并发/速率限制是可另设的资源约束，不取代 P1、P2 等各自的并发配置。单概念查询/补查/阅读额度及全批请求额度按各自作用域计数，不能按 worker 重置；重试同样占相应资源与请求预算。
- 同一概念只有本轮已安排任务完成、失败或因预算/超时明确结束后，才按既定交接策略进入审定。以概念、轮次、问题、请求及材料标识关联结果，保留失败和未读范围，不依赖完成顺序；共享查询/网页复用不能丢失概念关联。
- 流式处理与持久化提交分别验收：需明确逐条或有界小批保存、恢复及去重边界，不能把计算完成描述成已经写表。首次 P4 建树仍需明确批次和固定审定范围；P3 基于固定树版本可并发挂载，不并发逐条改树。

源码核对：demiflow 的 `map_async` / `map_prompt_async` 支持每级独立 `concurrency`、`queue_depth`，本地流式执行器创建各级 worker 和有界队列，支持级间重叠执行。但当前 `preparation/concepts/concepts_pipeline.py` 在全部 P1、全部取证、全部 P2 后分别物化并写表，属于阶段内部并发、阶段之间整批等待；`RetrieveQuery` 内多个网页也按循环串行获取。当前流式算子链不能直接承接普通 `join/reduce_by_key`，采用概念行方案后不以新增这种跨粒度能力为前提。行内有界子任务、请求复用及增量持久化仍须结合已有平台能力落实并验证，不能声称只拆几个并发参数就已经实现端到端流式。必要的通用执行能力按既定边界沉淀 demiflow，业务问题与补查决策留在本模块。

#### 3.8.1 交接与保存设计（2026-10-01 已确认方向，参数待定）

主线按以下可见节点组织，所有箭头仍交付概念行：输入 → P1 → 搜索 → 获取与解析 → 读取材料 → 首次 P2 → 条件补查搜索/获取/读取 → 条件第二次 P2 → 最终结果。首轮与补查复用同一套取证能力；第二次 P2 使用同一 prompt 职责及模型，传入本轮额度、先前材料与判断，不新增业务 prompt。

| 概念节点 | 接收当前行中的内容 | 交付当前行中的新增内容 |
| --- | --- | --- |
| P1 | 原始概念身份、名称和带来源的待核线索 | 候选解释、核验问题、有关联的查询计划 |
| 搜索 | 本轮查询及问题关联 | 候选集合、查询执行状态；保留原排序与来源 |
| 获取与解析 | 候选、已知待获取链接及本轮额度 | 固定材料引用、结构信息、逐请求状态和实际用量 |
| 读取材料 | 固定文档引用、核验问题或补读请求及阅读预算 | 文档引用、选定原文块的位置与顺序、提供范围、未读范围及选择记录 |
| P2 | 原始线索、计划、实际提供的材料、执行状态与轮次 | 逐问题结果、概念结论、明确缺口及有优先级的补查请求 |

- 补查在主线上显式展开为至多一次的后续节点序列，不由行函数隐藏循环调用模型。无需补查的概念跳过这些节点的实际搜索/获取/模型动作，保留原结论流向交付；只需补读的概念可跳过搜索和获取。技术失败仍按既定状态保留，不伪造业务结论或通过丢行结束。
- 行内长期携带概念身份、结构化控制信息、状态和固定结果引用；网页原始快照及大正文不在每个下游阶段反复复制，P2 调用时按预算读取已选定材料。记录行内对象的逻辑延续，不要求所有节点原地修改同一个内存对象。
- 保存分为两层：平台按请求保留搜索/获取状态、材料版本与模型原生调用记录，业务按概念和阶段保留可恢复的交接记录及最终结果。相同请求仅在身份、配置和材料版本相容时复用；超时且执行结果未知的模型请求先核对状态，不直接重新发送。
- 建议阶段结果通过主线上显式的有界提交节点逐条或按小批保存，目标表、schema、提交策略在入口可见；提交成功才标记该阶段已持久化。正常尾批需要提交，意外中断留下的未提交工作由已保存的请求/材料记录恢复；不承诺进程中每个结果都已落盘。
- 小批条数、最长等待时间、各节点并发/队列、内部子任务并发、共享服务额度及具体持久化接口尚待确定。存储方向按第 3.9 节最新确认执行；本节不是运行配置，不改变已确认的阅读/补查额度，也不授权启动实现或运行。

| SQLite 原生调用/控制记录 | 模型请求身份、原始请求/响应、预算预留和错误；必要的提交控制记录 | 防止重复调用、核对结果未知的请求、记录提交回执；不另存一套概念业务真源 |

- 主线保持一行一个概念，阶段表按概念及轮次记录，继续位于 `preparation/concepts/datasets/` 并以 run 区分。独立文档可供多个概念、多个阶段和后续消费者共同引用；本期不以接入或重写历史文档库为前提。
- 保留输入、计划、取证、审定四类主要业务记录：取证记录包含查询/候选/请求状态、文档引用、实际选定块的位置与顺序、未读范围；审定记录区分首次与补查后的判断。后续树与挂载继续独立版本化，不回写原 master 或覆盖 08 冻结树。
- 独立文档的逻辑内容包括原始快照引用、解析正文与章节/块结构、原始/最终 URL、取得时间、解析器版本与配置；原始响应字节仍单独保全，解码与解析不覆盖原始文件。复用 demiflow 的通用内容寻址对象能力，通用文档封装、引用、读取和校验机制归 demiflow；业务指定存储位置、解析配置与选段策略。字节相同的对象可复用，但不同来源与取得记录仍保留。
- 各表统一保存独立文档引用，核心为 `uri + sha256`，必要时附大小、格式等读取元数据。该 URI 指向本地或对象存储中的固定文档对象，不是实时网页地址，也不是 Lance 内部记录；具体文档封装/schema 在实现前明确。文档内容或解析版本变化时产生新对象/引用，既有引用指向的内容不改写。
- 概念身份沿用已约定的 `concept_id` / `source_record_id`，不以模型建议的规范名替换主键。保留原名、规范名、名称关系及审定依据；按原名找到旧图片的关联继续保留。
- 网页取证引用采用独立文档 URI 与 SHA256，再附该版本内的有序块选择、必要上下文位置和读取策略版本；读取时直接打开文档对象并核验，不先查询另一张 Lance 材料表。业务数据来源、阶段结果及树版本仍按其既定的固定版本契约保存；模型记录使用原生 journal 路径与 request ID。P2 输入在调用边界从文档引用读取、按已选位置组装，原生调用日志继续记录实际完整请求供核对，不只记录 token 数或摘要。
- 每张可变目标表由受控 writer 串行提交，前面的概念计算仍并发。建议由平台提供主线可见的有界小批提交能力，按条数或等待时间刷新，尾批正常提交；批量阈值继续讨论。不在每个 worker 内独立追加同一张 Lance 表，也不在行函数里创建子 Dataset。
- 保存顺序为：原始快照及其固定文档对象落盘并核验 → 提交引用这些对象的概念阶段记录 → 登记提交回执并向下游交付。对象存储、Lance、SQLite 不是一个跨库事务；通过提交顺序、稳定记录身份和回执核对恢复。只有请求日志已成功而阶段表尚未提交时，可复用请求结果补写；提交结果未知时先核对目标记录与版本，不能假定失败后再次 append。
- 审定及材料以新版本/新记录保留历史，第一轮和第二轮判断不互相覆盖；恢复以请求/输入/配置/材料身份匹配为准，而非“同一个概念曾经成功”。运行配置或 prompt 改变时按既定新 run / 新请求身份处理。
- Markdown 为固定版本的只读导出；业务表、原始对象、模型原生记录各自只承担上述职责。对象引用仍被使用时不能按普通缓存删除。

源码依据与限制：现有概念模块已使用明确 schema 的 Lance 阶段表和 SQLitePromptJournal；`journal_options` 将历史 `.lance` 调用定位转为 `.sqlite`，不是把模型日志写回 Lance。当前 `DOCUMENT` 的 `text/raw_text` 嵌入 EVIDENCE，RESULTS 又内嵌完整 evidence，后续需按已确认的独立文档引用方案调整。demiflow `LocalObjectStore` 已提供按哈希原子发布和核验，`DatasetCommit` 提供追加意图与不确定提交保护，Lance checkpoint 提供整段结果的固定版本保存；这些能力不能直接等同于已经接通统一文档格式或概念流水线的增量提交。本轮仅记录确认方案，不新增存储服务、数据表、下载或迁移任务。

### 3.10 P1→P2 首版剩余项统一建议（2026-10-01，待用户统一确认）

用户要求把所有待定项与补充建议统一输出。本节汇总建议值，不将它们自动升级为已确认配置。第 3.6、3.8、3.9 节已确认的阅读/补查额度、概念行主线和独立文档存储方向保持；当前仍不实现或运行。除执行前必须核对的服务限制外，建议按本节形成一组可配置但首轮冻结的默认参数，不增加常驻模型审核、网页摘要或粗筛/精筛节点。

**A. 独立文档封装与读取**

- 首版采用 UTF-8 JSON 作为独立的规范文档对象，包含 `schema_version`、来源元数据、`raw_ref`、解析器版本/配置摘要以及有顺序的章节/原文块。原始响应字节是另一个不可变对象；原始快照先保存，规范文档再引用它。JSON 是文档载体，不封装整条概念业务结果。
- 表中统一的文档引用只需 `uri + sha256`，可附大小/媒体类型。块标识只在该文档版本内解释；阅读引用由文档引用、选定块 ID/顺序、所属问题、必要上下文位置组成。不能用 URL、文档标题或 Lance 行号代替固定文档引用。
- 读取请求采用全文、指定章节/块、围绕问题选段三种方式，统一返回实际提供范围、未提供范围和 token 使用记录。正文与上下文进入模型前按实际 tokenizer 计数，同一块去重一次；章节标题、表头、图注保留。引用集合只包含实际提供给 P2 的块。
- 首版取证支持 HTML 和纯文本，不自动启动浏览器渲染、OCR 或 PDF 处理；不支持类型明确记录，并在候选/补查额度内寻找其他来源，不能用摘要冒充正文。格式支持范围是本次建议，不是已验收能力。
- 同 run 的相同查询/语言/服务参数、相同网页获取请求可复用成功的固定结果；同时重复请求合并执行，概念关联分别保留。跨 run 默认不自动沿用旧搜索/获取结果，需要复用时显式指定来源与刷新策略；对象字节可继续按哈希去重。概念的逻辑取证额度和全批实际外部请求次数分别计数。

**B. 并发与队列**

以下队列与外层并发的单位均为概念行；首轮与补查的同类节点采用相同默认值，各自配置，同时受共享服务限额约束。

| 节点 | 节点并发 | 输入队列深度 | 每概念内部并发 |
| --- | ---: | ---: | ---: |
| P1 | 4 | 4 | 不再嵌套模型调用 |
| 搜索 | 8 | 8 | 2 个查询 |
| 获取与解析 | 8 | 8 | 2 个网页任务 |
| 读取与组装材料 | 4 | 4 | 2 份文档 |
| 首次 P2 | 4 | 4 | 不再嵌套模型调用 |
| 补查后 P2 | 4 | 4 | 不再嵌套模型调用 |
| 每张阶段表的 writer | 1 | 64 | 不再嵌套 writer |

- 同一模型服务全流程最多 8 个在途请求；搜索服务最多 8 个；网页获取最多 16 个。同一网页主机最多 2 个在途获取、每秒最多放行 1 个请求。共享闸门是额外上限，不能替代各节点配置，等待闸门不持有实际网络请求槽位；重试与重定向同样遵守限额。
- 小批提交建议最多 32 条、首条进入批后最多等待 5 秒，任一条件先到即刷新，正常结束刷新尾批。每张表一个受控 writer；写入位置/schema/模式在主线可见。批次记录稳定键与内容摘要，先保存提交意图、再写表、核实回执后交付下游；不确定提交先核对，不盲目 append。
- 上述是保守的起始配置，没有吞吐测量支持，不能宣称最优或据此保证完成时间。队列满时向上游传递等待；有界队列不等于整个进程 RSS 已被严格封顶。仅调整调度参数不改变相同请求的复用身份。

**C. 超时、获取大小与技术重试**

| 项目 | 建议默认值 |
| --- | --- |
| 网络连接超时 | 10 秒 |
| 搜索、网页获取单次尝试的总时限 | 各 30 秒，包含连接和读取 |
| 单文档解析/读取时限 | 各 30 秒 |
| 模型调用单次时限 | 600 秒 |
| 存储锁等待 | 30 秒 |
| 每次网页获取 | 传输及解压后分别最多 2 MiB；重定向合计计入该次尝试 |
| 规范文档对象大小 | 最多 8 MiB，超限记录失败，不删正文后伪装完整 |
| 网页重定向 | 最多 3 次，整个获取仍受 30 秒总时限 |
| 搜索/获取的临时网络失败 | 最多重试 1 次，即共 2 次尝试 |
| 模型传输或 schema 失败自动重试 | 0 次 |
| 解析、读文件、哈希不符自动重试 | 0 次，保留具体错误 |

- 时间从获得执行资源并开始相应操作时计算；排队等待单独计时。阻塞操作的真实取消/退出需要验收，不能把线程调用的外层协程超时当作工作已停止或允许释放槽位继续增加在途工作。
- 普通临时网络失败重试前等待约 2 秒并加少量抖动；429 优先遵守 Retry-After。若要求等待超过 60 秒，本轮记录限流未完成，不在较短时间内强行重试。404、已识别的验证码/登录拦截、空正文、确定的不支持类型不重复请求同一候选，可在既定候选额度内继续选择。
- 服务鉴权/模型名等全局配置错误、持久化写入失败直接停止新任务并保留已有结果；同一模型或搜索服务连续 5 次连接失败/5xx/限流且无成功，停止向该服务派发新任务，记录需恢复。单个网页失败只影响其记录，不熔断整个搜索/模型服务。
- 模型自动重试关闭时，超时、无效结构、输出被截断或引用越界均记技术未完成，保留原始响应。补查后的 P2 是最多一次的业务再审定，与技术重试分别计数。全部取证因技术故障失败时不伪造 P2 结论；正常无结果可形成有效未决。补查技术失败保留首次有效判断，并单列未完成的补查状态。

**D. P1、P2 与全批额度**

- P1 建议完整输入最多 8,000 tokens、输出最多 4,000 tokens；候选义项最多 4 个、核验项最多 8 个，沿用现有数量级。核验项非空，查询总数仍按已确认的 4 个（含原名）执行；优先保留名称对应、范围和核心视觉内容，不凑满。
- P2 沿用已确认的首轮材料 12,000、补查新增材料 6,000、第二次累计材料 18,000、完整输入 32,000、每次输出 8,000 tokens。第二次完整输入含首次材料、判断与新增执行记录。完整输入超过上限时不调用，不静默截断；输出上限及推理 token 如何计入需要在实际服务上核对。
- 模型固定为 `malasci/gpt-6.1-sol`。执行前核对实际 tokenizer、请求模板/schema 开销、上下文和输出容量、用量及计价口径；现在没有服务单价与延迟实测，不填预计金额或工期。

**E. 补充的质量与验收建议**

1. 原名到候选对象的对应关系单独核验。搜到某个物种/器具的资料不等于证明原名指它；类别、物种、品种、型号、阶段等范围不得为了确定性或出题而偷偷收窄。概念成立也不要求每项都是现实个体或具体物种。
2. P2 可以纠正 P1 假设和补入遗漏问题；每项已核事实都要绑定实际已读的原文块及适用条件。程序校验结构、引用和版本，模型判断语义支持性；不按来源数量或问答完成比例自动通过。转载/镜像不充当多份独立证据，单份足够直接的可信资料也不强制再找第二份。
3. 身份、核心内容、视觉任务方向和执行状态分开。原名保持/等义规范化、范围改变、未解决分别处理；改义不自动接管旧图。视觉呈现建议标为模型设计推论，不冒充来源事实或实际图像观察。
4. 长文验收对照原始快照，检查否定、条件、例外、表头和跨段含义是否丢失。网页文字只作为证据数据，不执行其中的指令。不新增模型摘要或网页质量打分节点。
5. 工程验收至少覆盖：查询/别名关联保全、中文原名与英文正确结果、部分失败与全失败、空结果与拦截页、正文超预算、引用未读块、同请求复用、补查一次停止，以及模型已返回/对象已保存/Lance 已提交各处的中断恢复。测试应通过正式入口和隔离数据，不把伪造响应当作真实质量验证。
6. 全量运行范围仍为 3,315 条。建议完成后固定随机抽查 100 条有效审定（不足则全查），另查所有范围改变、来源冲突及结构/引用异常，区分随机样本与定向样本的统计用途。直接复核原始证据，不把同一模型两次一致当作独立验证，也不据此宣称所有概念准确。技术失败和未决保留在完整范围中。

本节的参数值是待确认的统一建议；具体变量名、文档 schema 与平台接口在认可方向后按规范实现，不再把每个字段命名升级成额外业务决策。当前未执行模型、搜索、下载或试点。
