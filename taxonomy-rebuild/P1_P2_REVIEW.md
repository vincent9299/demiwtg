## 1. 交付结构与实现边界

业务主图在 `preparation/concepts/concepts_pipeline.py` 的 config、run_pipeline 和 run_audit 中。固定来源、输入映射、阶段表 schema、每个模型节点、补查分支、独立并发和写入目标均可直接检查，没有在行算子中隐藏模型循环、子 Dataset 或全表扫描。

`operators/audit.py` 负责一个概念内的查询关联、候选配额、阅读安排、逐问题校验和补查执行边界。`operators/concepts.py` 保留原身份、P1 契约、身份/任务检查及采纳规则；旧的按整批拼正文、按字符取开头及“任一网页失败便阻断审定”的实现已移除。`operators/schema.py` 明确结构化业务字段，`operators/settings.py` 集中运行默认值，`operators/metrics.py` 只收集执行观测。

P1/P2 的正文与响应契约唯一维护于 `prompts/tasks.yaml`。P1 保持“输入和你掌握的相关知识均需核实”的原则；P2 增加逐问题结果、真实原文块引用、首轮/第二轮交接和有目的的补查。主图只调用这两个角色，不增加网页判定、摘要、粗筛或精筛模型。

平台新增独立文档、受限网页请求、共享请求准入、队列观测、token 档案校验及受控流式 Lance 写入。原生模型运行时增加可选共享 gate 和 token_budget，缓存命中不占新请求名额。通用实现不导入 demiwtg，不包含概念、物种、出题或具体表路径规则。平台 API 与使用边界见 [demiflow 文档](../../demiflow/docs/web_evidence.md)。

## 3. Review 中发现并修正的问题

第一，流式批处理原本会复制可调用实例。如果直接用外部 writer 实例读回版本号，可能得到未更新的版本，进而把有数据的表报告为空。正式主图改为绑定受控实例的方法，回执来自实际执行的实例；平台文档明确这一点，并增加尾批和版本回归。

第二，若在异步查询缓存读取前后分开判断进行中的请求，会有相同请求重复发出的竞态。现在先登记共享任务，再由该任务读取持久回执；跟随者等待同一任务。失败和预留中断也留下回执，重跑不会重置同一请求的尝试额度。

第三，重定向时如果一直占用旧主机许可，再去获取新主机许可，可能在主机之间形成互等。现在每跳完成后释放上一主机，再在同一总期限内获得下一主机许可。搜索服务与网页主机节流也分开，避免把整个搜索服务意外限制为每秒一次。

第四，补查资料的阅读顺序起初把所有旧文档补读放在新文档之前，这会违背 P2 的优先级。现已统一按请求顺序分配材料预算，并在每个请求内保留问题之间的阅读机会。章节补读明确展开到下一同级或更高标题，包含子章节，不把“读标题块”冒充读完整章节。

第五，判断“没有新增材料”时不能一律称为技术失败。正常空搜索、重复资料和预算限制需要和网络/解析失败区分。现在只有相应技术失败且没有可用新增材料等情况才标为补查技术未完成；请求重复、超额、无效定位和未完整阅读均有明确回执。

第六，输出 schema 中可空对象不能只依靠外围 schema 校验。对 task_sketch 和文档引用补入了严格的结构和类型检查，坏响应留在原概念行，不能因 AttributeError 让整批失败。引用检查使用实际阅读块集合，不构造假正文来适配旧接口。

第七，资料解析失败时也要能够检查原始响应。获取成功后先保存原始快照，解析失败仍交付 raw_ref 及来源元数据；不支持的 PDF 不被假装解析成功。文档散列、结构和文本编码损坏均有明确技术错误。

第八，鉴权、客户端配置和存储错误应停止调度，不能产生几十万条重复错误请求。共享模型 gate 将相应错误提升为全局停止，401 案例验证只有一次请求且没有隐藏重试。初始化和运行异常均保存失败摘要，避免失败后长期显示 running。

第九，长文选择中反复建立集合和对已累计材料重复计数会产生不必要的平方级工作。已经改为复用候选集合、已读集合和当前 token 计数；选择本身也在有实际进程期限的隔离边界运行。仍需真实长文与规模负载测量，不能只凭这些改动宣称 40 万条性能已经验收。


第十，真实请求证明计数不能只依赖一个从短提示词拟合的常数。固定 schema 变长后出现系统性偏差；当前档案显式记录 system 正文计数两次的服务计数规则，逐条对照实际 usage。平台支持可选 role_content_copies，实际文字材料计数仍为正常编码计数。该规则不推测上游隐藏消息，也不冒充模型官方 tokenizer 说明。

第十一，真实 P2 将没有明确 nullable 类型的 schema 解读成必须填写对象，五条 hold 返回了占位草案，按业务约定被正确拒绝。平台现支持具体类型与 null 的联合声明，继续严格校验非空对象的子字段；任务草案与文档引用改用明确 nullable schema，不再依赖省略 type 的技巧。对应 P2 版本提升，真实修复验证中 null 正常交付。

第十二，P1 曾输出“检索权威资料、比较并记录……”这样的长工作指令。P1 prompt 已明确 query 必须是直接提交搜索引擎的关键词串，并给出名称到分类的例子。真实修复后的三个 P1 均生成了可执行查询；这不能单独保证搜索服务返回相关资料。

第十三，原配置的新增材料额度没有先扣除完整 P2 的固定提示词、目录、首轮判断和失败回执。真实第二轮达到 33,800–35,401 tokens，超过 32,000，上游花费已经发生但第二轮被正确拒绝。现用同一原生模板先检查完整上下文，只收缩本轮新增的完整块，在阅读回执明确记录；旧证据和首轮判断不动。预算不能满足时仍返回 context_budget。正式入口与直接编排案例都覆盖这一边界。

第十四，恢复测试发现并发获取按完成时间插入字典，导致 fetch_results、目录和材料顺序变化，重跑的模型请求发生变化。现在按原查询和候选顺序稳定排列文档，问题和查询关联也按确定顺序排列；特意反转两个网页的完成顺序，结果必须完全相同。最终真实重跑单独核对新增调用数，不能再只用单网页 mock 宣称所有情况都复用。

第十五，原生节点 max_requests 的既有语义是当前节点执行额度，不自动等于 SQLite 日志生命周期额度。业务首次实现只配置前者，导致同 run 的变化请求可以在下一次调用得到新额度。现在业务主图同时将节点额度和 sqlite_journal.max_requests 显式设置，SQLite 在原子预留时按整个日志累计限制。平台保留其他消费者原有节点额度语义，不做全局破坏性改动。真实联调中已发生的额外请求保留且计入总量，不把它们删掉或冒称缓存命中。

第十六，环境直连不能完成网页获取，已增加明确的 fetch_proxy_url；它仅影响网页，不能把本地搜索服务发往网页代理，且进入请求身份。隔离解析的 subprocess.TimeoutExpired 统一转成 TimeoutError，以便保留原始快照并登记技术失败。模型 HTTP 408 通过 call.http_status 区分为 model_error，不冒充输出 JSON 的结构错误。

第十七，性能复核发现重复使用的行函数或模型节点名称会合并统计并错配队列。平台为每个拓扑节点分配稳定的独立名称，计数、处理延迟和队列位置逐一对应。业务测试的网络 fixture 另限定到本目录，避免跨仓组合收集时拦截平台测试自身的本地 HTTP 服务；该测试隔离问题和生产网络问题分开修复。

## 4. 恢复、规模及诚实的能力限制

阶段输出采用“新交付快照、小批追加”的方式。重跑保留旧固定版本，从固定输入回放当前交付，复用模型日志与网页回执；没有实现任意跨存储事务，也没有宣称按业务行原地更新。重跑仍有读取、计数和写阶段表的成本。writer 的唯一键控制集合随输入数增长；队列有界不意味着整个进程 RSS 恒定。

全局中断后已经完成的小批保留，未执行项由固定来源、明确选择与 scope_count 界定，摘要为失败/中断。不会为了填满结果表而给尚未执行的概念捏造否决结论。正常完成的正式交付按主键核对输入/输出覆盖。

HTML 结构提取不能机械保证清除所有语义广告、转载、伪科学或拼接文章。这些情况由 P2 判断，并依赖真实质量复核。PDF/OCR/浏览器渲染、历史正文关联、图片下载和图片审核没有偷偷纳入本轮。

默认模型路由已经按用户选择配置，但路由名不证明 tokenizer、消息包装或服务容量。真实校准与正式 P1/P2 的 usage 已用于建立当前服务的计数档案，详情见性能报告。它记录实测请求计数和有限准入范围，不冒称厂商容量保证。40 万条稳定吞吐、资料召回率和总体事实正确率仍未验证；真实网页测试暴露了搜索服务的明显质量问题。
