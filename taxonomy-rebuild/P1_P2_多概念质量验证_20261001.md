# P1→P2 多概念质量验证与修复记录

本记录归属 [preparation/concepts](../preparation/concepts/README.md)。全部业务运行经该模块的 `config → run_pipeline`，使用用户指定的 `malasci/gpt-6.1-sol`、HTTP 流式传输、真实搜索和下载。输入来自 `datasets/master_concepts.lance@4`，公共概念表和图片表没有修改。本文区分程序完成、身份核实和任务方向可用，不将其中一个指标替代另外两个。

## 1. 验证范围与结论口径

前两轮选取 12 个问题类型不同的实际概念：天牛、Crassula Ovata、Brassica Oleracea Var. Alboglabra、母狮无鬃、六角扳手、Flutist、Give Me Five、文氏图、禁止停车黄网线、Axe木棒、茭白、苏式月饼。这组样本用于发现错误，特意覆盖科级类群、物种与种下名称、性别限定、工具、角色、动作、抽象关系、地域规则、混合名称、食用部位和地方食品，不能当作总体准确率的随机样本。

修复后的第三轮重复这 12 个概念，并增加事先登记、未用于提示词调优的 6 个概念：肉锥花、蒜薹、Agate Geode、Chinese Zodiac Animals、三角龙化石、砍骨刀。两类样本分别解释：已知失败样本检查修复效果；新增样本检查是否出现明显的泛化问题。小样本全部完成也不能证明 3,315 条或 40 万条达到同样质量。

运行目录统一位于工作区 `_demiflow/concepts_quality_20261001/`。每轮有独立配置、原生 SQLite 模型请求日志、typed Lance 阶段表、独立网页对象和固定版本回执；没有把监控脚本变成另一套生产流程。

## 2. 前两轮实际发现了什么

| 运行 | 实际提示词及搜索配置 | 技术交付 | 时间及模型用量 |
| --- | --- | --- | --- |
| `quality12_baseline` | P1 第 4 版、P2 第 3 版；Wiki 两个引擎；语言 all | 2 条完成、7 条首轮取证失败、3 条补查失败 | 451.11 秒；19 次模型调用；输入 127,605、输出 29,395 tokens |
| `quality12_current` | P1 第 5 版、P2 第 4 版；Google；语言 all；共享搜索启动间隔 1 秒 | 首轮 12 条都取得可读材料，最终仅 1 条完成；9 条补查输入超额、1 条引用无效、1 条补查失败 | 618.03 秒；25 次模型调用；输入 417,307、输出 55,999 tokens |

第一轮不能称作“新版提示词验证”：实际请求日志显示它使用的是旧版。过程中观察到 `tasks.yaml` 两次回到旧内容，而用户确认没有其他修改；排查未找到明确写入者，导入业务代码和短时间监视也没有复现写入。这里只记录观察，不将原因归咎于用户或猜测外部进程。第二、三轮都冻结了实际文件，并核对原生请求中的版本。生产入口现在还会将实际加载的 prompt 版本与内容散列写进日志和运行摘要，防止今后仅看当前文件误认历史请求版本。

两轮模型传输均未出现 HTTP 408。第二轮所有 25 次调用都有响应，输入 token 本地计数与服务返回 usage 一致。因此“模型正常返回”和“业务流程可用”必须分开看：这一轮的主要失败发生在材料组织和业务引用校验，而不是模型 HTTP 超时。

### 2.1 搜索引擎和语言设置影响召回，不能只怪关键词

原 Wiki 关键词适配在 `language=all` 时回退到英文；中文概念容易拿到弱相关的英文列表。并发请求又出现 429 和引擎暂停，SearXNG 即使返回 HTTP 200，正文也可能只有引擎错误。此前程序在 HTTP 200 时先重置故障计数，掩盖了连续搜索失败。

独立探测中，Bing 对这组查询出现无关结果，Brave 和 DuckDuckGo 出现限流或验证码；Google 配合 all 语言取得了直接相关结果，例如 `Axe Bat wood` 返回厂家木棒目录，`Brassica oleracea alboglabra` 返回植物资料，中文苏式月饼和天牛也能召回中文页面。这是当前部署和当前查询的实测，不表示某个引擎永远最好，也不表示搜索结果天然可信。

第三轮显式采用已经探测过的 Google/all 配置。平台增加按会话共享的搜索启动间隔，并在解析搜索正文后判断技术健康。真正的正常空结果与引擎失败继续分开；语义上是否相关、可信仍交给 P2，不恢复旧 collect 的名称命中硬筛。

### 2.2 正文清理误删了真正的内容

旧解析器将包含 `sidebar` 片段的 class 都当成侧栏。实际网页的 `has-sidebar`、`sidebar-right`、`ast-no-sidebar`、`l-sidebar-right` 是整篇文章或 body 的布局标记，结果正文被一起删除。后续 fallback 又把页面 head 中的 title 当作了正文。

修复后只移除明确的部件容器，保护正文和布局根节点；优先识别 article-body、entry-content、main，避免把第一张导航卡片或第一条商品评价当作整篇文章；标题作为元信息，不进入空正文 fallback。解析版本升级，原始网页快照保留，旧规范化对象也不覆盖。

| 已保存的真实网页 | 修复前正文字符数 | 修复后正文字符数 | 说明 |
| --- | ---: | ---: | --- |
| Webike 六角扳手介绍 | 31 | 3,815 | 原来仅剩标题，现恢复主体文章 |
| Hanstool 六角扳手分类页 | 66 | 972 | 恢复产品分类内容；是否足以证明定义仍由 P2 判断 |
| Succuland 景天科文章 | 22 | 2,591 | 保护含布局类名的内容区域 |
| Lessonface flutist/flautist 文章 | 33 | 3,050 | 恢复名称说明文章 |
| Aspect CrossFit high five 文章 | 42 | 2,092 | 恢复文章正文 |

这些是同一份保存的原始字节前后重放，不把重新搜索到不同网页造成的差异归功于解析修复。剩余限制仍包括动态页面、视频正文、PDF、登录和验证码；不能因为下载状态正常，就称资料足够。

### 2.3 中文词匹配挤掉了其他语言的证据

原阅读策略将所有文档的段落放在一起做词匹配排序。问题是中文时，中文长文持续得分，已经下载的英文资料却一直没有正文交付给 P2。模型看见目录但看不见正文，只能再申请补读。

平台现先执行明确的补读位置，再在每篇文档内部按问题和相邻上下文组织候选，为不同文档分配阅读份额，剩余额度继续复用。完整原文块不被截断，前一轮证据不被替换，绑定关系仍在计量之前合并。这是技术上的阅读安排，不是让平台判断哪些观点正确。

同样的旧文档、同样的 P1 问题、同样 12,000 token 材料上限下，“母狮无鬃”的中文百科由 33 块改为 13 块，两篇英文保护机构资料由 0/0 块变为 8/9 块。文氏图的英文欧拉图资料也由 0 块变为 6 块。这一改善不依赖提高预算。

### 2.4 补查输入重复太多，而且首轮未为第二轮留空间

第二轮必须保留首轮材料和判断，这个约束本身正确。但首轮在组织输入时重复发送文档位置、完整 SHA、URL、标题、HTTP 尝试日志，第二轮又叠加新回执和上一轮判断。即使零新增材料，六角扳手输入仍达到 36,415 tokens，苏式月饼 36,365，Axe木棒 35,067，超过原来的 32,000。

业务现在将 P2 来源信息按文档统一列出，正文用文档编号关联；搜索和获取的状态及失败原因仍提供，但完整网络尝试日志留在可追溯的阶段表中，不重复塞进模型。正文、反证、上一轮审定没有因压缩而被删除。

首轮新增上下文保留量配置；平台计量的仍是最终实际请求。适配先测试全额度，再测试零新增材料；如果必要材料能装下，最多做六次本地额度探测，返回已经计数合格的结果。这里没有新增模型调用，也不保证找到所有块的全局最优组合。旧 11 条补查输入在使用新业务载荷、保留旧证据和判断后，均能装入原 32,000 上限，其中有新正文的记录也能继续加入材料。

### 2.5 长引用编号被模型抄错

文氏图首轮回答的一条证据引用把 64 位文档散列抄错了几个字符。原校验器正确拒绝了它，没有自动找“最像”的引用。修复不是放松校验，而是在 P2 输入中分配当前请求内唯一的 `E1`、`E2` 等短标签，并以 `selected` 中的稳定顺序作精确对应。返回后恢复完整引用再校验，未知标签仍拒绝。

业务表继续保存完整引用，原始模型请求和响应保持原样。Markdown 对模型说明文字里出现的短标签提供对应关系，不能把不同概念中的同一个 E1 误当作同一段证据。

## 3. 为什么仍然取证，为什么补查应减少

模型已有知识在 P1 中用于理解名称、提出候选解释、识别错别名和反例；不要求模型假装什么都不知道。P2 对拟采纳的身份及核心事实核对实际正文，是为了避免用第二个模型的流畅回答替代对第一批 AI 生成数据的审核。取证并不是编写完整百科。

前一轮 12 条中 11 条提出补查，明显偏高。一部分是下载和阅读程序没有交付已有好材料，另一部分是模型要求解释所有变体、全部历史别名或旧作者本意。这些并不都影响当前决策。

P1 第 6 版和 P2 第 5 版明确：主体与限定能够有依据、无歧义地组合时，不要求它逐字作为词典条目出现；没有年龄限定就保留未限定范围，不自行猜一个年龄，也不因无法恢复作者心理而无限暂缓。身份已清楚，且已有一个可靠、可观察的核心任务方向时，旁支缺口可以保留，无需占用补查。真正涉及品牌、误译、多个合理义项或范围变化时仍应保留不确定性。新的停止要求是减少无意义补查，不是预设概念必须通过。

## 4. 预算扩展与计费口径

用户在验证过程中明确要求扩展预算。相同模型、相同网关、相同流式方式完成一次 64,000 输入加 8,000 输出额度的准入校准，实际输入 usage 为 64,000，输出 12，耗时约 6.97 秒。调用先前因本地未设置 API-key 环境变量而没有发出请求；配置本地网关占位 key 后才真正调用。校准成功只说明这个请求容量被接受，不证明模型最大的容量或长文本推理质量。

| 参数 | 前一轮 | 当前扩容验证 |
| --- | ---: | ---: |
| P2 完整输入上限 | 32,000 | 64,000 |

## 6. 自动验证与实际限制

平台 web/document/reading 和概念完整入口测试共 63 项通过，另新增短引用恢复、未知引用拒绝及完整 Markdown 展示的入口测试 1 项通过；概念相关布局检查 5 项通过。测试包括 malformed HTML 中正文保全、标题不充当正文、跨语言阅读、旧证据完整保留、正常无结果与技术失败分开、一次补查、精确引用、持久请求复用与原名身份。它们证明工程行为，不替代语义审核。

目前没有对图片做生成或评审，`task_status=ready` 只是有依据的任务设计方向，不能声称已经测出模型视觉差距。来源可能不充分、搜索可能变化、PDF/视频/动态页面正文可能未获取，模型仍可能误读证据或过于保守。凡确实存在歧义或缺少关键资料，应交付未决及理由，而不是为提高成功率放宽审定。

原生模型流式传输、流取消传播和 map_prompt_async 的相关测试另有 52 项通过，包含服务故障时完整响应保存、原请求超时仍生效、不发布被取消行，以及普通主动取消。该故障收尾修复在第三轮失败之后完成，不能声称第三轮已经受到新保护。

## 7. 第三轮的实际结果与停机原因

`quality18_optimized` 在 484.81 秒时以 `ServiceStopped` 失败结束，不是完成 18 条。18 条输入全部登记；15 条完成 P1，14 条留下首轮取证快照，其中 13 条技术上可读；最终审定表提交 6 条。其余 12 条在 Markdown 中明确标为尚无最终交付，没有按“不成立”处理。

| 已交付概念 | 身份 / 任务 | 是否补查 | 内容复核要点 |
| --- | --- | --- | --- |
| 天牛 | 已核实 / 有任务方向 | 否 | 保持科级类群范围；任务选木中幼虫，不将成虫长触角条件套用到幼虫 |
| 六角扳手 | 已核实 / 有任务方向 | 否 | 保持工具类别；平头 L 形作为本题实例限定，没有把它写成所有六角扳手的定义 |
| 砍骨刀 | 已核实 / 有任务方向 | 否 | 依据刀身与刃部结构提出任务，不凭外观断言精确重量、钢材或厚度 |
| 三角龙化石 | 已核实 / 有任务方向 | 否 | 保持属级化石材料范围；区分化石原件、复制与补配。角方向任务引用保存的原研究摘要，并限定为该研究的生长系列；未因存在次要缺口一律补查 |
| Axe木棒 | 未决 / 暂缓 | 一次 | Axe 品牌木棒与跨品牌斧形握把木棒存在真实范围歧义；厂家页面还显示不同握把系列，不能强行合并 |
| 苏式月饼 | 已核实 / 暂缓 | 一次 | 补查的标准说明帮助确认概念身份；支持视觉任务的酥皮层次与机制资料仍不足，身份核实不等于出题可用 |

这里的 4/6 不需要补查只描述先完成的六条。复杂或较慢的概念更可能尚未交付，存在明显的完成顺序偏差，不能用它估算全批补查率，更不能与前一轮 11/12 直接当成严格对照效果。

原生日志共登记 27 次模型请求，23 次完整响应，4 次本地取消；已知输入 246,047、输出 38,585 tokens。四条取消调用分别涉及 P1 的 Flutist、Give Me Five，以及首轮 P2 的肉锥花、茭白。前三条已收到 HTTP 200 或部分流内容，最后一条未收到正文；没有收到 usage 的调用不能按零费用计算。本轮没有观察到新的 HTTP 408。

搜索缓存留下 60 条查询回执：55 条正常，2 条 CAPTCHA，3 条 Suspended: CAPTCHA。SearXNG 服务在 12:17:15 UTC 记录 Google 验证码，随后按配置暂停该引擎 3,600 秒；连续五条搜索技术失败使平台停止新调度。原执行器直接取消了正在执行的模型请求，形成上述四条本地取消。这是此次新增有界收尾保护的具体原因。

## 9. SearXNG 的可用性与历史配置

本轮选择 `search_engines=["google"]` 是试跑配置，不是给 Google 分配付费配额。SearXNG 负责请求与聚合，当前 Google 适配器使用搜索网页，仍会遇到上游验证码；其引擎暂停是本地保护机制，不能保证到期时 Google 恢复。[SearXNG Google 适配说明](https://docs.searxng.org/dev/engines/online/google.html)。

实际配置为搜索并发 2、启动间隔至少 1 秒，出网经过已有 HTTP 代理。Google 官方说明，自动化流量及同一网络上其他用户的自动化请求都可能引发验证码；现有日志不能区分请求节奏、出口信誉或同出口其他流量的贡献。[Google 异常流量说明](https://support.google.com/websearch/answer/86640?hl=zh-Hans)。不能把这次验证码归因于中文关键词，也不能把模型并发 8 当作这次故障的原因——验证码发生在更早的模型并发 4 试跑中。

用户提醒旧采集也曾频繁搜索后，重新核对了旧实现：`collect/operators/text_engines.py` 的文档请求只指定 `categories=general`，未限定 engines；部署模板继承默认引擎，并额外启用 Google、Bing、Yahoo、Qwant、Mojeek、Mwmbl、Fireball、Yep、wikisearch、360baike 等。因此旧文档链是多引擎聚合，可以在一个引擎失败时仍返回其他引擎的结果，不能将旧成功归因于 Google，也不能断言旧流程没有用 Google。图片链另用 images 分类和领域路由，不等同于文档链。

只读查看旧 `collect/datasets/documents.lance@4` 的前 100 条，确有百科和普通网站记录；样本里的来源保留 query、URL、wiki/serp 标签，但未保留可确认的具体搜索引擎。该顺序样本不能代表全库质量，也不能用模板替代历史部署与成功率证据。旧 wiki dump 导入还绕过逐概念网页搜索，历史总下载量不能等同于搜索请求吞吐。

下一步先比较旧聚合范围内各引擎在当前部署的成功、相关结果和错误来源，保留引擎归属；不能因 Google 小样本相关就固定单源，也不能因某次其他引擎失败就认定所有替代源长期不可用。接着验证多源配置的持续可用性。必要时将搜索降为单并发、每 5 秒最多启动一次；这个值是待测配置，不是厂商认可的安全速率。尚未完成全量放行，不启动 3,315 条。

结合适配器默认分类，旧模板中静态属于 general 且未禁用的条目有 20 个：wikipedia、bing、yep、currency、wikidata、duckduckgo、fireball、google、google cse、lingva、mwmbl、qwant、startpage、yahoo、dictzone、mymemory translated、mojeek、brave、wikisearch、360baike。其中包括汇率与翻译，仍不能等同于 20 个可替换 Google 的全网搜索源。实际数量必须以逐源可用性与相关性验证为准；当前有相关结果证据的 Google、wikisearch、wikipedia、Mwmbl 也承担不同功能，不能简单相互替代。

## 15. 公共文档与运行缓存的边界核对

用户追问已有 Wikipedia 文档能否避免重复下载，并指出资料应当公共。当前实际状态是：`Dataset.fetch_documents` 的下载与解析机制在 demiflow，原始字节和规范化文档在独立对象目录，Lance 只保存引用；但 URL 到已有文档引用的获取缓存放在各 run 的 `retrieval.sqlite` 中。因此同一 run 可以跨概念复用、恢复时不重下，跨 run 或跨 pipeline 则尚未实现完整的公共获取复用。对象按 SHA256 去重，不等于请求前已知道本地存在该 URL 的合适版本。

只读核对现有 `demiwtg/collect/datasets/documents.lance@4`，表内共 22,279,894 条混合来源文档记录，不把此数当作 Wikipedia 条目数。对 wiki 行的有界顺序样本中，AccessibleComputing、AfghanistanHistory 保留重定向目标；Anarchism、Albedo 保留语言、page_id、revision_id 和 26 个分节，分节正文仍包含 `{{...}}` 模板与 `[[...]]` 链接语法。它们是实际已有资产，但不是当前网页算子输出的规范化正文块。未扫描全量统计质量，也未导入、改写或下载这些记录。

目标边界已登记到 DF-012：搜索查询缓存、公共文档对象及来源定位索引、各 run 的获取/使用回执分别管理。既有文档导入与在线下载都登记同一公共文档契约；获取算子先查共享索引，匹配语言、页面/URL、版本与更新要求后直接返回引用，未命中才联网。导入必须保留原始格式与版本，正确处理重定向和 wikitext，不能伪造为新下载 HTML。将公共资产提供给获取算子不等于建成了本地搜索引擎；若要免除线上关键词搜索，仍需独立的本地检索源。此处是明确的待补平台能力，不写成已经实现，也不将全库迁移扩大为当前试跑的前置任务。
