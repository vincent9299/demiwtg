## 1. 目标与不可变约束

目标是让既有概念更适合按视觉对象浏览、采集、标注和分析，同时尽量保持概念集合不变。首批及两批冻结交付采用严格保全：不新增、删除、重命名、合并或拆分原概念，只调整其上方的分类树，并增加独立说明。后续生产设计允许经核实的规范命名与知识描述修正，但必须保留原记录、身份关系和改动依据，不能通过覆盖原名丢失旧图片关联，详见第 11 节。

输入的 `id`、`group`、`concept` 是保全字段；树路径、属性、名称粒度和审核状态是可调整字段。同义词只能关联，例如 `Mooncake` 与“月饼”保留两个原始记录。原组别保持 1 / 2 / 3，不自动解释为难度、地域性或稀有度。

本批 ID 根据原组别与原行序生成，例如 `1-008`。它们只在本批内有身份意义；后续换批次应加 `batch_id`，不能把同一个 `1-008` 当成项目全局概念 ID，也不能通过名称相似度直接覆盖主库记录。

**全量重建的来源前提：**用户明确说明旧分类树由较弱模型多次生成，概念也由 AI 生成。旧路径只作为待核查的历史信息保存，不能直接成为新树骨架、正确标签或整枝迁移依据。概念成立性与含义审核是必要阶段；保全原文不等于确认概念真实、明确。逐概念旧路径实际存在于 `master_concepts.lance`，只是先前粘贴的汇总文本没有提供。40 万规模的方案以第 9、11 节为准。

## 2. 这次实际如何处理

1. **拆开原表。** 原文按组提供二级类目列表、三级类目列表和概念列表。提取出 464 个概念，保留原文、组别和顺序，建立 ID。原文没有逐概念旧路径，所以无法做真实的逐条“旧路径 → 新路径”对照；没有用列表位置猜配对。
2. **明确分类用途。** 先对比了视觉导航与知识领域导航，之后按用户选择只继续视觉版。这里“视觉”指以对象、部件、图示或场景组织概念，不保证仅凭外观就能分辨所有物种、型号或具名实体。
3. **逐项分析目标是什么。** 区分生物、器物、建筑、图示、人物、活动与场景等；把物种身份与品种、年龄、动作、部位等附加信息分开。例如“雪豹幼崽”仍以动物为主体，幼体属于属性。
4. **归纳三层导航树，再逐条挂载。** 根据这批实际概念整理上层分组，每个 ID 分配一个主路径。检查同层分组是否便于使用，对交叉条目制定优先归属规则，最终得到 15 / 67 / 179 个类目；没有先定数量再凑分支。
5. **记录难例与依据。** 对影响分类的名称查资料；缺少上下文或含义有歧义时保留暂定路径和问题说明，不擅自换名称。身份、呈现形式和归属不确定性分别记录。
6. **单独核查生物名称粒度。** 检视动物、植物、真菌三个一级类目的 166 条名称，区分科、目、纲、属、多物种通名、品种、部位和状态组合。重点问题形成 21 条“未到种”和 10 条“待确认”，并附能找到的依据。此步骤不是图像鉴定，也没有完成全部名称的物种级审定。
7. **机械检查保全与覆盖。** 把概念原文、组别、顺序与原文件逐项比较，核对 ID 集合及每条在主树中的出现次数，检查路径深度与类目统计。
8. **生成可阅读交付。** 将名称粒度标记直接显示在视觉树的概念后，并生成集中说明。按照用户偏好，当前交付使用 Markdown，知识库版和 CSV 停留在历史材料状态。

其中第 2–6 步包含本次助手结合上下文和资料完成的语义判断。`build.py` 保存的是这些判断的结果，`audit_visual_leaves.py` 保存的是这批审核结论；运行脚本不会重新进行这些推理或在线核实来源。

## 3. 分类业务规则

| 情况 | 主树处理 | 独立信息 |
| --- | --- | --- |
| 生物名称加年龄、性别、行为 | 主体仍为生物时，按生物归类 | 年龄、性别、行为写属性；有主体歧义则待核对 |
| 明确以活动或环境为目标 | 按活动、场景或环境归类 | 不因出现动物或植物词就强行归生物 |
| 整体、部件与表示形式 | 分开组织 | 植物、植物部位、植物结构图不能混为一种目标 |
| 具名器物、型号、地标 | 按对象类型进入主树 | 身份、用途、文化背景可作属性或说明 |
| 已加工食品 | 按食品或菜肴组织 | 原料关系不替代食品主归属 |
| 虚构生物、文化形象 | 按虚构或文化形象组织 | 不混入真实生物物种集合 |
| 品种、科属通名、复合名称 | 原文保留 | 粒度单独标注，不靠改树冒充改细了概念 |
| 同义、翻译或相关概念 | 保留原有记录 | 只记录关系，不自动去重合并 |

最终已发布的视觉主树中，一个概念只有一个主路径。存在多重用途时，先决定标注目标的主体，再选父类；其他合理关联写入属性或关联说明，避免同一个概念在导航树中重复计数。处理阶段无法明确含义的记录保留待处理状态，不能为满足覆盖率硬分一个类；未决记录仍计入全量完成的分母。

本批植物交叉归属按“明确部位 → 多肉与肉质类型 → 木本 → 水生湿地草本 → 其余草本与藤本”处理；药用、观赏、食用可另记属性。这是本批的导航约定，不是科学分类等级。新批次如需修改优先顺序，应明确受影响的概念并重新审查。

父类应能合理容纳其下概念，同层尽量按同一判断依据组织。三层仅是当前导航深度；不要求每层都对应科、属、种，也不要求每个概念本身都是物种。

## 4. 名称粒度必须与主树分开

“科”和“目”是不同的生物分类等级，“科目”不是一个正式等级。不能把所有非物种名称统称为科目。

当前 Markdown 使用以下显示规则：

| 显示或状态 | 含义 | 不能据此推断什么 |
| --- | --- | --- |
| `未到种·科/属/…` | 名称明确指较宽类群，或类群加标本形式 | 不意味着名称错误，也不要求立即拆成物种 |
| `待确认` | 通名可能指类群，也可能特指一种，当前不能确定原意 | 不能算作已证实的高阶类群，也不能算已到种 |
| 品种、部位、幼体、行为 | 描述概念形式或附加属性 | 不自动等于高阶类群；来源物种仍可另行核查 |
| 无上述标记 | 尚未列入重点问题清单 | 不等于已完成种级核验 |
| `归属待核对` | 主体、含义或导航位置存在问题 | 不等同于名称的生物分类等级 |

审核时必须区分三件事：名称的形式、用户原本指的对象、科学数据库中的分类地位。某通名在一个来源里对应具体种，不能据此保证本输入一定也是该含义。属只有一个现生种，也不使属名在名称层级上变成种名。

未来记录应将 `taxon_rank`、`name_scope_status`、`concept_form`、`placement_status` 分为独立字段。非生物概念设为不适用；缺证据保留未知。只有存在明确对象对应和可检查依据时，才标记“已核验到种”。当前旧字段不能无证据批量映射成已通过。

## 5. 固定成标准 pipeline 的阶段契约

下面是通用实现应遵循的业务阶段，不代表冻结交付已经全部执行。当前批次的整理判断已有快照，但尚未完成全量成立性核验；不能直接把已有归类转成已核验概念。

2026-09-30 讨论收敛：下表视为业务检查项，不要求各自建设独立执行阶段。最新提案见 v0.3：共同审定概念及核心内容、核对分类并交付，下游正式出题；粗筛/独立精筛不再默认串联。图片处理由现有 preparation 后续承担，本期只保留名称与定义交接。

| 阶段 | 输入 → 输出 | 放行条件 |
| --- | --- | --- |
| 1. 冻结输入 | 固定主表版本及本轮范围 → 来源快照 | 原名、全部旧路径、来源身份可追溯；本期不要求图片表输入 |
| 2. 概念清洗 | 名称、上下文、独立证据 → 含义、类型、范围、成立性及规范化候选 | 生物按需核验分类等级；器具、型号、作品等按各自身份标准审核；证据不足保留未知 |
| 3. 确认身份关系 | 原记录、审核结果 → 稳定身份、规范名、原名关系与定义版本 | 改名不改变身份；同义关系有依据；消歧、拆分和范围变化不能伪装成改名 |
| 4. 设计或修订上层树 | 已明确概念、多样性样本、视觉导航规则 → 树版本候选 | 无环、无孤立节点；每个节点有边界；不把旧路径或组别当正确答案 |
| 5. 逐条挂载 | 概念身份、固定树版本 → 主路径、属性、理由或待处理状态 | 已发布记录恰好一个主路径；未决记录不丢失；每行不能自行发明父类 |
| 6. 下游概念交接 | 原名关系、规范身份、定义/限定与版本 → 交接结果 | 原名可追溯；实际找图、核对和发布归现有 preparation，不阻塞本期交付 |
| 7. 审阅与局部修订 | 概念与树的问题清单 → 有依据的修订决定 | 变更有前后值；只重新处理受影响项；树调整不自动改概念身份 |
| 8. 验证并导出 | 同一轮固定结果 → Markdown、摘要及结果引用 | 来源全覆盖，关系无悬空，未决项单列；结构通过不冒充语义准确 |
| 9. 发布或下游接入 | 审定结果及兼容性核对 → 主数据新版本或下游输入 | 保留历史版本和旧名查图能力；概念身份、分类与出题潜力分别记录，正式题目继续核对最终任务 |

树设计需要查看全批的分布和边界案例；逐条挂载则必须共享同一个候选树版本。不能让每行自行发明父类，最后仅把字符串拼成树。

持续输入时，先向现有树挂载已明确概念，再汇总无法容纳、边界混杂或规模失衡的问题，按批次修订树并重审受影响的旧概念。未决概念进入问题队列，不因输入一条新概念就重建整棵树。图片核对与树维护可以在身份明确后独立开展；有无可用旧图不决定概念是否成立。

知识判断可以由人或模型提出候选。使用模型时，按仓库规范保存 prompt pack、响应结构、实际模型与输入版本；不假装已有标准 prompt 可以完整复现此前交互判断。确定性的解析、计数、覆盖检查和渲染由代码完成。

## 6. 通用实现的数据契约

正式工程化使用 Lance 保存业务输入和结果，跨阶段传 Dataset 或固定 DatasetRef；Markdown / JSON 只作查看导出。通用存储、并发、预算、缓存与 notebook 规则直接遵循仓库规范，不在本目录另建执行框架。

以下是建议的最小业务结构，具体 Arrow schema 在实现时定义：

| 记录类型 | 粒度与主键 | 必要信息 |
| --- | --- | --- |
| 原概念快照 | `(source_uri, source_version, source_record_key)` 一行 | 原文、别名、全部旧路径；存在时保留原组别、原序号和批次 ID |
| 规范概念 | 每个稳定 `concept_id` 一行 | 规范名、对象类型、身份范围、定义版本、审核状态与证据引用 |
| 名称解析决定 | 每个来源记录在某一解析版本中的每个目标一行 | 原名、目标身份、关系类型、依据及是否已确认；一对多不得当同义自动合并 |
| 树节点 | `(tree_version, node_id)` 一行 | 父节点、类目名、导航层级、归属规则 |
| 主挂载候选 | `(batch_id, tree_version, concept_id)` 一行 | 目标节点、主路径、属性、归属理由、归属状态；发布后挂载以主表为唯一权威 |
| 名称审核 | `(batch_id, audit_version, concept_id)` 一行 | 名称范围状态、分类等级、概念形式、对应对象、说明、证据 |
| 旧图关联与复用判断（后续 preparation） | 每个概念身份、图片 SHA、定义版本及审核协议一行 | 历史名称与固定来源、图片 URI、候选/可用/不可用/待确认、依据与原审核引用；非本期必交表 |
| 审阅决定 | 每项问题的每次明确修订一行 | 对象 ID、修订字段、前后值、原因、来源、决定状态 |

证据至少包含来源 URL 或文献标识、来源支持的具体判断、实际查阅时间；来源提供版本或稳定分类 ID 时一并记录。历史记录缺少的时间、学名或审核人保持缺失，不能事后伪造。

`tree_version` 与 `audit_version` 分开：移动一个器具的父类不应让未变化的动物名称判断无故失效；名称上下文、身份解释或审核标准改变时，则必须重新判断审核能否复用。

以上是逻辑记录，不要求每种记录都新增一张公共主表；正式字段和阶段结果表在实现时确定。项目正式主数据与本批概念 ID 之间需要显式映射，不能按同名覆盖。当前主表没有 `concept_id`，不能把建议字段写成已存在能力。未审核记录仍以来源身份保存，不能因尚无规范身份而从审核结果中丢失。

概念与挂载统一由 `master_concepts.lance` 保存，不恢复已退役的独立 `concept_taxonomy.lance` 权威表。名称解析关系服务于身份追溯，并不是另一套分类挂载真相。接入时以实际目标 schema 为准；如存在挂载元数据则同步维护，不能依据旧文档假定其仍存在或自动重建已删除字段。公共表只修改本流程负责的列。

## 7. 验收与完成状态

必须按概念身份对账，不能只检查总数。对于本批，验收基线如下：

- 464 条原名、组别、顺序、ID 逐项不变；组别分别为 25、225、214。
- 输入 ID 集合与树中 ID 集合相等，每个 ID 恰好出现一次；不存在缺失、重复、多出或悬空挂载。
- 每条主路径包含三个非空导航类目；树无环；计数与实际挂载一致。
- 审核记录指向本批真实概念，名称和当前路径一致；主树标记与详细清单来自同一次审核结果。
- 未到种 21 条与待确认 10 条分别计数，未审核和不适用不冒充已到种。
- 相同输入与判断重跑，交付内容保持一致；更换输入后旧批次脚本必须拒绝继续。
- 在迁移后的目录可独立重建；知识库历史材料和 CSV 保持原字节。

新批次的数量来自其冻结输入，不能继承 464 的固定常量。节点数量也由实际树决定，15 / 67 / 179 是本批结果而非通用目标。

完成状态分开报告：**结构完成**表示概念保全、覆盖及路径校验通过；**语义审阅状态**说明尚有哪些归属或身份问题；**正式发布状态**表示是否已经接入项目主数据。结构完成可以同时存在待确认名称，不能因此宣称科学审核全部完成。

## 9. 不可靠旧树下的 40 万概念重建

### 9.1 旧树的使用边界

先前提出的“先按旧分支建立映射，再仅处理少量例外”依赖旧分支已经相对可信。在用户明确旧树由弱模型多次生成之后，该前提不成立，不再作为本项目的全量默认方案。

旧路径保留用于回溯、比较变更和发现历史冲突。第一次独立归类不把旧路径当作正确答案，也不以它限定唯一候选集合。确需查看旧路径来消歧时，应明确其来源不可靠，不能把它单独作为放行证据。旧分类统计描述的是历史组织方式，不能证明存在同等数量的合理类别。

现有 464 条新视觉树是设计原型，尚不是完整的科学分类标准，也不是独立人工审定的评测集。不能用其自身的生成结论证明同一方法准确，更不能把它的 179 个三级类目视作 40 万概念的完整覆盖。

### 9.2 建议执行顺序

1. **保全输入并审核概念成立性。** 用户已确认概念也由 AI 生成。从固定主表版本读取原名与来源，核查指代对象、身份范围和依据，标记歧义、疑似错名、复合描述、非视觉目标等。没有可靠来源时保留未知，不擅自纠正或删除。原名、规范名、同义、拆分等关系必须显式记录，历史图片关联继续可查询。
2. **独立发现全量内容分布。** 使用随机样本、名称特征及语义近邻分组来覆盖常见、稀有、跨语言和边界概念；不能只按旧树分层抽样。向量分组用于找相近概念和代表样本，不直接定义正确分类。
3. **建立并审阅新树。** 按视觉任务明确每类的定义、纳入条件、排除条件、正反例和同层划分依据；结合可靠领域资料。强模型可以协助提出候选结构，人工与外部依据负责校正边界。树只在明确的修订阶段变更，逐条分类阶段使用固定版本。
4. **构造独立验证集。** 将用于设计类目、示例或调整规则的样本与验收样本分开。验收标签需人工或有依据地审定；模型之间一致不等于事实正确。
5. **给每个概念生成候选并判定。** 先检索少量新类目候选，再依据类目定义选择；候选不合适时保留待处理并扩大检索。试点验证过的明确规则或分类器可处理常规项，冲突、歧义和缺依据项交给更强模型或人工复核。不能仅凭向量分数或模型自报信心批量放行。
6. **评估后分批扩展。** 分别检查候选是否包含正确类目、自动接受项的准确性、待处理比例以及各领域表现。对罕见类目、跨类边界和分歧项额外抽查；树规则修订时重新检查受影响范围。

向量检索用于候选召回，技术依据见 [Sentence Transformers 语义检索文档](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)。依据分类概率设自动接受阈值，需要先评估概率校准，参见 [scikit-learn 自训练阈值示例](https://scikit-learn.org/stable/auto_examples/semi_supervised/plot_self_training_varying_threshold.html)。这些方法的文档不构成本数据集上的准确率或成本保证。

### 9.3 成本与试点验收

每条概念都要经过处理，但不要求每条都调用一次大模型。可复用的成本来自固定类目定义、短候选列表、经验证的规则与分类器、内容一致的结果复用，以及只对疑难项做深入查证；不能靠假定旧分类正确来省略检查。

“仅 10% 的记录需要模型”只是一种预算情景，当前没有实测覆盖率支持。先在 2,000–5,000 条多样性样本上试点，记录不同处理路径的真实 token、额外推理、重试、数据库查询和人工复核开销，再按全量分布估算。向量计算和本地模型也有资源成本，不能一律记为免费。

试点至少报告：独立验收集来源和规模、各领域准确性、候选召回、自动接受率、未决率、原概念保全率、模型实际消耗。预算不能只按成功或容易的样本估算；若新树覆盖不足或概念本身不明确，应先修订或补证据，不能通过强制分类降低未决率。

此节更新设计规范；尚未启动全量重新分类或付费模型处理。

## 10. 两批合并交付规范（v1.2）

### 10.1 本轮身份与保全

首批 B1 为 464 条，新批 B2 为 2,975 条。原始来源实体共有 3,439 条；124 个跨批完全相同的名称在显示层各聚合一次，得到 3,315 个显示概念。这是显式保留来源的视图聚合，不是把两个来源实体静默合并。跨批同名可能仍有不同语义；13 个组别不同的同名项同时保留两种来源组别，不选一边覆盖。

原名称不进行 trim、大小写统一、翻译、纠错、同义词合并或拆分。来源 ID 为原批内 ID 加批次身份；首批概念保留原 ID，新批独有概念用 `B2-{group}-{index}`。每个显示概念只有一个导航主路径，来源数组覆盖全部出现记录。

本轮使用的粘贴文本没有逐概念旧路径关系，不通过汇总列表的顺序伪造映射。后来提供的 `master_concepts.lance@4` 有实际逐概念路径，且覆盖全部 3,315 个名称，后续可据此做真实的旧新路径对照；该核对尚未回写本轮冻结判断。首批视觉方案只能作为本轮候选，不能成为独立评测答案。

### 10.2 决策与执行分离

本轮采用“当前 Codex 会话整理和复核判断 → 固定判断快照 → 脚本检查并导出”。候选构造使用同类名称规则、字符串辅助和明确例外，之后按类别展开复核；这属于模型辅助整理，不是规则本身证明分类正确。没有额外调用模型 API，也没有独立第二模型或专家复审。

`combined-decisions.json` 保存原名、主 ID、来源、路径、判断基础、概念形式、名称粒度、归属状态及说明。`combined-manifest.json` 固定两份输入和判断快照的 SHA-256。`build.py` 默认合并版，显式 `--combined` 同义；`--visual-only` 保留首批回放。

新增 `combined_view.py` 只校验和渲染，不从新名称自动生成判断，不联网、不写主表。它是本次 Markdown 交付的回放组件，不登记为已上线的生产 pipeline。真实生产接入仍需履行仓库 PIPELINE_SPEC 的完整要求。

### 10.3 状态与未决项

`name_audit.status` 与 `placement_status` 独立；`concept_form` 表示品种、部位、阶段或场景等概念形式。没有全面核验种身份的情况下，生物名称默认“未核验到种”，不批量升为“已核验到种”。有依据才能写具体等级；没有依据的通名判断明确其来源是本轮名称分析。

“待明确主体”是未决工作区，保留在主 Markdown 末尾并计入总分母，不是已确定对象类别。“抽象与文化主题”保留载体问题，不宣称可直接作为单对象视觉识别类。各类节点深度不代表统一的生物分类等级；部分具名对象归类也不意味着能够凭图片唯一识别其身份。

### 10.4 必过检查与交付

原始输入哈希、判断哈希、原名集合与首次出现顺序、来源数组与组别、ID 唯一性、路径合法性、全量单次挂载均通过后，才生成 08–10 Markdown、08 树 JSON 与检查摘要。旧 01–07 文件和 CSV 不被合并版回放改写。负例测试必须确认输入或判断不一致会阻止输出；重复回放应产生相同内容。

结构检查通过不能写成语义准确率。报告必须披露未决条数、没有独立语义验收、未接入图像验证及未完成全量科学定种。当前“最终版”表示两批合并交付的固定版本，不表示所有未知项已解决。

完整过程和本轮来源依据见 [09-合并与质量检查](09-合并与质量检查.md)。下一批需要重新做语义判断与复核；不能仅替换输入并更新预期计数就认为自动分类已完成。

### 11.2 三种判断分别回答什么

| 判断 | 核心问题 | 输出不代表什么 |
| --- | --- | --- |
| 概念清洗 | 这个词指什么？对象或类别是否有依据？名称、身份范围、描述是否准确？ | 成立不等于物种，不等于能从外观唯一辨认，也不等于值得出题 |
| 视觉树维护 | 已明确的概念放在哪里，怎样浏览和组织最合适？ | 挂载成功不证明概念真实；路径改变也不改变概念身份 |
| 视觉任务潜力（现有粗筛/精筛的职责） | 核心内容是否值得测、能否形成有区分潜力且可靠判分的方向？ | v0.3 建议并入共同审定，结论仍与身份分开；hold 不等于概念虚假或应从主库删除 |

共同审定以 [完整出题 prompt](../benchmark/t2i/v2/prompts/tasks.yaml) 对核心内容、适用范围和可判断性的定义为基础，并参考 [精筛 prompt](../benchmark/t2i/fine_screening/prompts/tasks_batch.yaml)，不能直接把其 keep/hold 当作概念成立性标签。真实物种、科属类群、人工品种、器具类别、具体型号、作品、虚构形象和抽象概念应分别记录类型；并非只有具体物种或现实中的单一实体才是成立的概念。查不到资料先记“证据不足”，不能直接判“AI 编造”。

例如，一个范围明确的器具类别可以成立，但当前未必已有值得测的任务方向。两种结论可以在同一审定单元产生，仍分别保存；正式出题按最终题目继续核对。现有粗筛通常分配分类层面的投入，不能替代每个名称的成立性审核；新版不将其列为必经环节。

### 11.3 名称不是身份：保留原记录，另记规范化决定

建议为确认后的概念建立稳定 `concept_id`，名称和分类路径作为可变属性。该字段尚未落地；当前原记录通过 `(主表 URI, 固定版本, name)` 定位，两批来源 ID 另行保留。新 ID 一经分配不可因改名、翻译或移动分类而重算，也不能由当前规范名或 taxonomy 路径直接决定。

每次名称解析至少保存：来源身份、`original_name`、`canonical_concept_id`、`canonical_name`、关系类型、原意与规范定义、依据、决定状态和解析版本。关系可以待确认；没有确认的目标不能强行填入。原始 `aliases` 与已核实等价名称分别保存。

| 变化 | 身份与关系处理 | 旧图片的处理 |
| --- | --- | --- |
| 仅规范拼写、译名或表述，语义确实不变 | 同一 ID，记录 `same_meaning_rename`，保留原名 | 经原名找回同一批候选；已有审核是否可复用另判 |
| 两条原记录经核实指同一对象 | 显式 `equivalent_to`，多条来源指向同一规范身份；保留原 ID 与历史 | 合并候选集合，按图片 SHA 去重，保留所有命中来源 |
| 一名多义或原概念混合了多个对象 | `split_into` 或 `ambiguous`，必要时建立多个明确身份 | 原图不能全部复制为每个新概念的正例；逐图消歧，可仍然未知 |
| 改名实际缩小、扩大或替换了原范围 | 记录范围变化或身份修正；建立有谱系关系的新概念或版本 | 重新确认适配范围；不能按同义改名继承旧结论 |
| 只调整定义文字、知识描述 | 身份可不变，描述保留前后版本与依据；事实边界变化不能当纯措辞调整 | 核对图是否仍支持当前知识；旧模型请求和审核不能自动视作相同输入 |
| 只移动视觉分类路径 | 同一概念 ID，更新树版本和主挂载 | 图片资产关联保留；依赖旧路径作出的判断需检查是否受影响 |

例如，把“某类动物”缩成其中一个物种不是纠正写法；把“普通翠鸟雄鸟”去掉“雄鸟”也改变了范围。规范命名时必须保留性别、阶段、部件等原本有意义的限定。

### 11.4 从规范概念找回旧图片

本节保留未来图片接入契约。本期只完成原记录、名称关系与规范定义交接，不实际展开或审核图片；现有 preparation 的能力核对见 [v0.1 第 8 节](PIPELINE_PROPOSAL_v0.1.md#8-preparation-核对图片审核可复用本期只交接概念)。

查询关系如下；箭头中的名称关系必须来自已确认的解析决定：

```text
规范概念 ID / 当前名称
    → 已确认的原记录与历史名称
    → images.concepts 中命中的历史名称
    → 图片 sha256 + image_uri
    → 针对当前概念定义的复用判断
```

生产接入应先展开本轮历史名称关系，再与固定图片版本展开的 `concepts` 按名称关联，按 `(concept_id, sha256)` 汇总所有命中来源。保留没有图的概念、无法解析的历史名称和一名多义项的计数，不能用内连接后的成功行冒充全量覆盖。不能只用规范名查图片，否则改名后会漏掉原名下载的图。

需要区分三种状态：

1. **图片资产可定位。** 找到了 SHA 与 URI；实际字节可用性仍按现有图片流程检查。名称改变不要求复制图片文件或重新下载。
2. **候选关系成立。** 能解释为什么该图成为当前概念的候选，保留原名、来源版本和解析决定。候选可以来自错误的历史关联。
3. **图片可用于当前目标。** 审核图像是否支持当前对象、限定属性与用途；分别记录可用、不可用或待确认。一张图可以对甲可用、对乙不可用，也可以只适合宽类而不能用于种级判断。

已有图片描述、匹配、评分、`published_concepts` 和审核记录保留原始概念名、依据和版本，不能全表替换字符串或自动升级为新概念的通过记录。若决定复用历史审核，应显式记录所引用的原审核、同义证明、定义与审核标准的一致性及复用范围；缺少这些信息则仅复用资产和候选关联。

资产复用、审核结论复用、模型请求缓存是三件事。模型实际输入、prompt、模型配置或知识版本变化时，不能仅凭同一概念 ID 命中旧请求。知识版本变化要评估对审核的影响，不能简单认定所有旧结论都有效或全部无效。

### 11.5 增量更新与验收要求

先提交完整的规范化候选和关联核对结果，再发布新概念/树版本并切换下游读取；主表与结果表的固定引用由发布记录绑定。不能在新名称关系未准备好时直接覆盖公共 `name`，让仍按旧名工作的下载、筛选和审核流程断链。现有 08–10 冻结交付保持原样，新增审定结果使用新版本。

生产实现至少用以下情形验收：

以下涉及实际图片集合与图片判断的检查，在后续 preparation 接入时执行；本期检查原名/来源保全、定义与关系、分类、版本和发布契约，不将图片审核作为完成条件。

- 同义改名后，所有原图仍能通过已确认原名关系找回；来源记录不丢失，图片 SHA 和 URI 不因改名改变。
- 多原名合并后，同一图片在目标概念下只计一次，但全部命中来源保留；别名冲突不能静默选择第一条。
