# V4 融合世界标签体系 · 通用扩充方案（设计稿，2026-08-14）

> 状态：**设计稿（待评审）**。目标：不针对单一领域，建立一套适用于全部 1,253 个叶的**通用实例扩充管线**。

## 1. 背景与问题

V3 现状：1,253 叶 / 59,832 实例 / 叶均 47.8（中位 42，R8 后每叶 ≥38）。

两个结构性天花板：

1. **叶子粒度粗**：`内容作品 IP/影视作品/电影` 一个叶容纳所有电影 → 40 条就是手写枚举上限；真实知名影片数千部。
2. **纯靠生成**：V3 全部实例来自人工/LLM 逐叶枚举，R8 已把每叶推到 38-50，但量级上不去（LLM 枚举到万级即为极限，且存在虚构风险）。

用户要求：**不是只扩电影，而是找到一种通用方法**，覆盖所有领域。

## 2. 网络环境约束（实测 2026-08-14）

| 源 | 结果 |
|---|---|
| 豆瓣 `movie.douban.com` 页面/JSON 接口 | ✓ 可抓（需 User-Agent + Referer + XHR 头），中文片名+ID+评分 |
| 必应中国 `cn.bing.com/search` | ✓ 可抓，标题+摘要可解析，无验证码 |
| 百度 `baidu.com/search` | ✗ 302 反爬 |
| 百度百科 `baike.baidu.com` | ✗ 403 安全验证 |
| 求闻百科 `qiuwenbaike.cn`（中文维基镜像） | ✗ 阿里云 WAF 验证码 |
| Wikidata / Wikipedia / IMDb / DuckDuckGo 等国际源 | ✗ 不可达 |

**结论**：通用底源不能依赖国际维基/百度百科，**必应搜索（通用候选+验证）+ 豆瓣（内容类批量底源）+ 领域站点（按需）**构成可行组合。

## 3. 通用框架：E-C-V-A 管线

1,253 个叶共享同一条管线；每个叶只需配一条"数据源指令"（见 §4），其余全部通用。

```
            ┌──────────────────────────────────────────────┐
 E 抽取      │ 按叶的 source_type 分发候选获取               │
            │  内容源(douban_tag) | 列表源(bing_list) | 生成源(gen) │
            └──────────────────────────────────────────────┘
                            │  raw 条目流（带来源）
                            ▼
 C 清洗      │ 去重 · 去括号/注 · 去消歧/广告 · 长度过滤 · 置信度打分 │
                            ▼
 V 验证      │ 必应搜实体名，top 命中相关度 ≥ 阈值 才入库（防虚构）    │
                            ▼
 A 归属入库   │ 按叶边界规则归位 · 跨叶保留多视角 · provenance 记来源   │
```

### 3.1 E 抽取（按 source_type 分发）

| source_type | 适用叶 | 机制 | 实测 |
|---|---|---|---|
| `douban_tag` | 内容类：电影/剧/动漫/游戏/书/音乐 | 豆瓣 JSON 接口 `j/new_search_subjects`，按 tag（类型/地区/年代/组合）分页，`start=0,20,40...`；一次抓全部页。同 title 去重 | ✓ 200，返回中文 title+id+rate |
| `bing_list` | 枚举类：品牌/人物/赛事/奖项/非遗/地标/机构 | 必应搜索 `query + "列表/名单/大全/历代"`，解析 h2 标题 + 摘要，用 LLM 从摘要中切出实体清单；多条查询模板（"中国500强名单""奥斯卡历年最佳影片"） | ✓ 200，h2 可解析 |
| `gen` | 数据源覆盖不到的细分叶 | LLM 产出候选 → 必应逐一验证命中相关度，≥阈值收录（R8 放大版） | R8 已验证 |

### 3.2 C 清洗（通用规则）
- 去重（同叶内精确/去空白/归一化后去重）
- 去括号注（`肖申克的救赎（The Shawshank Redemption）` → 主名）
- 去消歧页（豆瓣 url 含 `subject/0`、空标题、纯英文、纯年份）
- 长度/字符过滤（过长或过短、含广告词）
- 置信度打分：来源类型 × 评分字段 × 验证命中数

### 3.3 V 验证（防虚构）
- 必应搜索实体名，取 top-N 结果的标题/域名，与实体名做相关度匹配（编辑距离/包含），阈值≥0.6 收录
- 对已自带 ID 的豆瓣条目（douban_id 存在）视为高置信，可跳过搜索验证，仅抽查

### 3.4 A 归属与 provenance
- 叶边界规则：`叶 → {include: [关键词], exclude: [关键词]}`（如"日本动画电影"叶 exclude 真人电影；"中国500强品牌"叶 exclude 外资）
- 跨叶不去重（沿用 V3 策略：同一实体允许多视角挂载），同叶去重
- 每条批量实例记 `{source, source_id, fetched_at}`，精选层实例记 `{source: "curated"}`

## 4. 叶 → 数据源指令（Leaf Source Spec）

每个叶配一条 JSON 描述，多数可由叶名启发式自动生成，人工复核后启用：

```json
{
  "leaf": "内容作品 IP/影视作品/电影/华语电影/中国大陆/90年代华语电影",
  "source_type": "douban_tag",
  "query": {"type": "movie", "tag": ["中国大陆", "1990年代"]},
  "target_min": 300
}
```

```json
{
  "leaf": "组织机构 IP/企业机构 IP/世界500强品牌",
  "source_type": "bing_list",
  "query": ["世界500强企业名单", "中国500强企业列表"],
  "extract": "company",
  "target_min": 200
}
```

### 4.1 源头决策：agent 为主 + 启发式预填 + 人工抽审

谁决定每个叶的 source_type 与 query？

1. **启发式预填（代码）**：规则清晰时直接命中——叶名含 电影/剧/游戏/书/音乐 → `douban_tag`；含 品牌/人物/赛事/奖项/名录 → `bing_list`。覆盖大部分，零成本。
2. **寻源 agent 决策（核心）**：对规则无法覆盖或存在歧义的叶，分块交给寻源 agent：读叶名、现有实例、父分支上下文，产出 `source_type` + `query` 模板 + `confidence`（如"文化带与线路"应搜什么词、能否用豆瓣）。产出写入 `specs/`。
3. **Auditor（质量闸）**：客观信号（豆瓣 ID 存在性 / 必应命中相关度）+ 按 `audit_ratio` 抽检裁判，精确率 < `precision_threshold` 即退回诊断，不再由人抽审。
4. **闭环迭代**：决策 → 试抓 → 若产出 < target_min 或验证通过率低 → 自动退回寻源重新决策（≤ `max_diagnose` 次），最终仍失败则降级 `gen`（LLM+验证）兜底，gen 不达标进待审池。

### 4.3 Agent 自治执行模型（已决策版，2026-08-14）

> scaling 的关键：**把"人参与"的环节全部替换为 agent，agent 行为由参数控制**。人只在定义层设置一次参数与总目标，之后全自主运行；仅两类介入——调参、看自动报告后的异常处理。

**两条正交轴**：执行轴（沿 E-C-V-A 流水线分功能）与治理轴（沿质量把控分监督），合并构成完整模型。

**控制面（人设置一次）** `v4_config.json` + `specs/`，全部为参数：

| 参数 | 值/默认 | 说明 |
|---|---|---|
| `target_min` | 每叶 override | 该叶采集目标量 |
| `precision_threshold` | 0.85 | Auditor 抽检精确率门槛 |
| `verify_min` | 0.6 | 必应 top-5 命中相关度阈值（豆瓣 ID 条目免验证） |
| `audit_ratio` | 0.05 | 新采实例随机抽检比例 |
| `max_diagnose` | 3 | Diagnoser 每叶最大重诊断次数 |
| `max_cost` | 叶级 token 预算 | 含寻源/重诊断/gen 全程，超限即停转待审池 |
| `daily_budget` | 全局日预算闸 | 全局每日 token 上限 |
| `concurrency` | 豆瓣串行 / 4 叶并发 / 必应 2 | 并发与限速（豆瓣 1req/2s 硬约束） |
| `confidence` | 寻源自评 0-1 | 供 Auditor 排序抽检 |
| 降级规则 | →gen→待审池 | 3 次后降 gen；gen 不达标进 `data/v4_raw/` 不硬凑 |

**执行面（无人在环）**

```
Governor ── 排序叶批次 / 分配预算 / 并发控制 / 日闸
  └─ 寻源 agent ── 产出 spec {source_type, query, include/exclude, target_min, confidence}
       │
       ▼
  Adapter（参数化确定性代码，预留 agent 扩展点）── 翻译 spec → 豆瓣/必应请求 → raw 条目流
       │
       ▼
  Engine E-C-V-A（确定性代码，幂等 / 限速 / 断点续传）
       │
       ▼
  Auditor（客观信号 + 5% 裁判抽检，precision≥0.85）
       ├─ 达标 → provenance 入库 → 下一叶
       └─ 不达标 → Diagnoser（≤3 次）→ 改 spec → 重试
            ├─ 超限 → 降级 gen → 仍不达标 → data/v4_raw/ 待审池
            └─ Auditor 异常频发 → 召 Reviewer 复审 spec（默认不启用）
```

**执行轴 agent 边界（已决策）**：
- 寻源：agent（选源 + 查法，需推理）。
- 源头适配：**参数化确定性代码**，预留 agent 扩展点（适配参数异常时可升级 agent 决策）。
- 采集：**纯确定性代码**（候选 + 下载，限速断点续传），预留 agent 扩展点（失败分类时）。

**治理轴角色（已决策）**：
- **Auditor**（第一道闸，每叶必跑）：客观信号优先——豆瓣 ID 存在性、必应 top 命中相关度、5% 裁判抽检精确率。核对基准不用黄金样本。
- **Diagnoser**（异常处理）：诊断失败原因（查太窄/太宽/语义漂移）→ 改 spec → 重试 ≤3 次。
- **Reviewer**（第二道闸，仅按需）：当 Auditor 连续失败或精确率掉线时召回复审 spec，默认不启用。

**风险备忘**：不建黄金样本 → 无 recall 度量（漏采测不出），只能测 precision。可接受（覆盖优先体系），但裁判抽检需同时看"采到是否正确"与"该类明显缺的知名实体"以部分补偿。

**agent 可信度依赖客观信号而非自觉**：豆瓣 ID 存在性、必应 top 命中相关度、抽检精确率；全量审计日志（每次决策/试抓/验证/抽检/降级留痕），事后可回溯复检。

**人在哪**：仅在设置层定义 参数/总目标/护栏（预算上限、禁止词）；周期查看自动审计报告，异常才介入。

**闭环迭代**：决策 → 试抓 → 产出 < target_min 或验证通过率低 → 自动退回寻源重决策 → 超限降级 `gen`。

### 4.2 启发式预填规则（按叶名）| 叶名特征 | source_type |
|---|---|
| 含 电影/电视剧/动画/游戏/书籍/音乐/纪录片/综艺 | `douban_tag`（细分 tag=地区+类型+年代） |
| 含 品牌/企业/公司/机构/人物/赛事/奖项/非遗/名录/列表 | `bing_list` |
| 地标类城市叶（已近饱和） | `bing_list`（当地著名景点榜单）或保持不动 |
| 其余细分叶 | `gen`（LLM+验证） |

## 5. 两层实例模型

```
精选层  curated   = 现有 59,832 条（人工/LLM 把关，质量优先，采集优先级高）
批量层  bulk      = 数据源导入（带置信度，量大；采集按抽样）
```

- 每叶展示时精选层在前，批量层在后
- 批量层置信度 < 阈值的降级到 `data/v4_raw/` 待审池，不直接入正表

## 6. 构建管线（scripts/v4/）

```
scripts/v4/
  specs/            # 叶→源描述（JSON，启发式生成+人工复核）
  fetchers/
    douban.py       # 内容源抓取（幂等、缓存到 data/v4_raw/、限速 1req/2s、分页循环）
    bing.py         # 列表源搜索（幂等、缓存、多模板）
    gen.py          # 生成源（LLM 候选 + 必应验证）
  clean.py          # C 清洗（通用规则）
  verify.py         # V 验证（必应相关度）
  assign.py         # A 归属 + provenance 注入
  build_v4.py       # 主入口：E→C→V→A，输出 data/ip_instances.json（同一文件原地并入、revision 自增，仅增不删，幂等）
```

设计原则：
- **幂等可重建**：raw 缓存于 `data/v4_raw/`，重跑零增量；`build_v4.py` 只把新增并入，不删旧
- **限速与断点续抓**：豆瓣 ≤1 req/2s，异常重试+指数退避；已抓分页断点续传
- **provenance 可追溯**：每条批量实例可回溯到 (源, id, 时间)

## 8. 采集配置策略（解耦）

- 实例层与采集层解耦：批量层不全部生成图片 job
- 图片采集只覆盖：精选层全部 + 批量层高置信抽样（每叶 top-N），job 量控制在可执行范围

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 批量层质量/语义归属错误 | C 清洗 + V 验证 + 叶 include/exclude 规则；低置信进待审池 |
| 豆瓣反爬升级 | 限速 + 断点续抓 + 降级到 `bing_list` 模式 |
| 必应反爬/结果被污染 | 多模板查询 + 标题相关度过滤 + Auditor 抽检 |
| 跨领域通用性不足（如地标已饱和） | 地标保持现状；`specs` 按领域由 Decider+Reviewer 复核 |
| agent 自治导致质量失控/自洽幻觉 | 客观信号优先（豆瓣ID/必应命中/置信度）+ 黄金样本集测精确率 + 交叉评审 + 全量审计日志；质量闸未过不进入正表 |
| 数据膨胀导致采集/存储不可控 | 两层模型 + 采集抽样（§8） |
| 中文标签缺失 | 豆瓣自带中文；bing 列表源要求结果含中文名才收录 |

## 10. 里程碑（试点先行）

**M1 多领域试点**（验证通用性，3-5 个代表叶）：
1. `内容作品 IP/影视作品/电影`（内容源，豆瓣）
2. `真人与人物 IP/体育明星/足球运动员`（列表源，必应）
3. `品牌 IP/企业品牌/世界500强`（列表源，必应）
4. `非遗与传统手工艺 IP`（列表源，必应"名录"）
5. `内容作品 IP/游戏作品`（内容源，豆瓣）

验收标准：每叶产出 200-1000 条真实、带 provenance、可重建；清洗/验证通过率 ≥90%；Governor/寻源/Adapter/Engine/Auditor/Diagnoser 全角色跑通（Reviewer 按需触发），全程无人工介入。

**M2 全量铺开**：Governor 启发式+Decider 生成 1,253 叶 specs → 全自主跑 E-C-V-A → 原地扩充 `data/ip_instances.json`（revision 自增）+ 新树（若需结构拆分）。

**M3 构建/展示/采集**：`build_v4.py` 接入现有构建链；更新 `tag_tree_explorer`（支持两层标注）；采集无需新配置（`--taxonomy data/ip_instances.json` 直读，新 revision 自动走增量）。

## 11. 与 V3 的关系

- V4 不推翻 V3：`ip_instances.json`（原 ip_instances_v3.json，2026-08-14 起中性命名）是精选层基座；树结构沿用，仅在需要时（如电影）做结构性细分
- 全链路保持 V3 的验收标准（幂等、去重、覆盖、无孤儿键）
