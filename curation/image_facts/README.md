# 缺口分析用图片事实

修改或运行本流程，必须先阅读并遵守[项目强制规范](../../PIPELINE_SPEC.md)。本流程为已选正例素材保存可检索的事实和详细 caption，并试验不同模型的标注一致性；不修改公共图片宽表，不恢复已退役的全库中性标注。

输入是 `t2i_positive_pairs` 已准备的概念行快照，需固定 URI/version，读取 concept、concept_id、selection_rank、positive_images。按 SHA 去重并保留全部概念关联和原审核引用。原概念名和旧审核不送给模型。当前用户授权 pilot 为 `inputs_v4__pilot10_target1024_20261004.lance@3` 的 10 概念、64 个唯一 SHA，含全部尺寸的图片，不依赖该出题流程是否合成成功。

正式入口为 `config → run_pipeline`，CLI 和 notebook 共用。Dataset 主线通过 read_lance、flat_map、reduce_by_key、group_batches、map_async、map_prompt_async 和 write_lance 完成固定流程。每模型独立看相同的缩略图，不读取其他模型答案，不需要 agent 动态选择工具。图片读取、校验和编码复用 `preparation/concept_positive_images/operators/pixels.py` 的单图处理函数；无跨 pipeline 执行。

配置 `configs/pilot10.json` 显式声明范围与模型：GPT-6.1-sol 和 GPT-6-luna 均使用 malasci、xhigh，每请求最多8图、并发2、各8次请求；Qwen3.5-4B 使用本地 vLLM、关闭思考、每请求1图、并发8、64次请求。vLLM 由标准 VLLMService 在首次未命中请求时启动，节点完成后释放，默认 GPU0。当前本地网关无鉴权，`MODELHUB_API_KEY` 使用非秘密占位值；已有环境值优先，不把提供商密钥写进配置；本地无鉴权服务的 `IMAGE_FACTS_LOCAL_KEY` 设置为非秘密占位值即可。模型总输出上限 GPT32768、Qwen8192 tokens；schema重试为0，无业务自动补请求。

图片按原比例缩至最长边1024、JPEG85、不放大不裁切，方向按 EXIF 纠正并将透明背景铺白；三模型共享这一处理方式。每张限制32MiB/6400万像素，每批编码限制16MiB，编码并发1。原始宽高从图片文件取得，保存输入编码 SHA；表内不存图片字节。记录的是此输入分辨率下可见的内容，不能把模型未发现的细字解释为原图没有文字。

标注字段：composition（单个主要对象/多个同类对象/多个不同类对象/无法确认）；objects（常用名称、图内ID、位置、可见特征、可辨数量）；relations（对象ID、有方向的关系、证据）；framing；view_tags；observability_issues；text；watermark；caption。具体枚举、定义和边界在唯一 prompt pack `prompts/tasks.yaml`。主要对象与背景/部件有明确区分，图内对象也可记录。未知数量保留 null；无观察问题使用空数组。

每次运行以独立后缀覆盖提交自己的 scope、各模型 labels、各模型 batches、comparisons 和 summary 表。labels 主键为 SHA×model_key；batches 保留请求级响应和调用引用；comparisons 为 SHA×model_key×reference_key×field。scope 保存 SHA 的所有原概念关联，labels 复制这些关联便于查看。所有 schema 显式声明。开始时固定配置和 prompt；同 run 参数变化拒绝执行。各模型完成后提交阶段表，最后写固定版本引用摘要，旧历史版本保留。断点复用依靠原生 SQLite 请求日志，不复制缓存或换 journal 绕过预算。

读取/解码失败、模型请求失败、schema失败或图片编号不匹配，保留全部受影响 SHA 为 failed。返回重复或遗漏编号时整批失败，避免错图绑定；模型关系引用不存在对象时该图失败。配置、资源、存储或程序异常终止。只有所有指定模型对全部输入图片都有有效标注并成功提交，summary.complete 才为真。

比较以 GPT-6.1-sol 作为约定参照，不是人工真值。固定枚举逐字段报告完全一致数/双方有效数，无法确认单独可查；多选字段比较集合。object_names_literal 仅是名称字面集合，不能把同义词差异算成语义错误；relation_types 也只比较类型集合，不等于对象关系完全一致。详细对象、关系、caption 必须结合图片抽查。失败不进入一致率分子，也不从完成分母移除。请求耗时、模型阶段墙钟时间、输入/输出tokens、重用数分别统计；批大小和并发不同，不能把这次墙钟速度当成模型纯推理速度排名。费用仅在有可靠计费数据时报告，不按猜测单价换算。

运行：在项目 Python 环境中执行 `python -m curation.image_facts.image_facts_pipeline --config curation/image_facts/configs/pilot10.json`。notebook 默认仅查看；显式开启才运行模型。查看读取已提交 summary 内的固定表引用，底层原生调用日志保存实际渲染请求、图像及参数。当前验证和真实结果在下方补充。

2026-10-04 验证：错图编号、无效关系对象和真实 Dataset/HTTP/journal 最小闭环通过3项测试（含独立输入和重复运行不重复调用）；本模块CLI、布局、规范引用和登记通过4项检查。首次启动GPT因占位环境未设置而未发送请求；现已前置环境验证。本地Qwen首版提示缺少完整输出字段示例，在34次保留调用（26返回、8中断记录）后停止；原日志保留于 runs/pilot10_64_three_models_20261004，不混入正式比较。正式试验使用 image-facts-2-complete-output 和独立 run pilot10_64_three_models_v2_20261004；所有模型使用相同正文和输出契约。

并行提交：同一份已固定的 run 配置可分别使用 `--model gpt61`、`--model luna`、`--model qwen4b` 启动三个正式入口进程，各持有独立模型锁和原生 journal；同模型重复提交拒绝重叠。新 run 先用 `--prepare-only` 建立 scope，此步骤持有全部模型锁且不请求模型；随后并行提交三个模型。本次并行时 scope 已提交，三个阶段读取同一快照。每模型提交 labels、batches 和 stage 固定回执；全部结束后用 `--finalize-only` 只读三个已提交 stage 汇总，不追加模型请求。串行入口和汇总也检查全部相关模型锁，避免和并行阶段重叠。生产 notebook 可传 `execute_models=[...]` 或 `finalize_only=True`；只读展示不需要模型环境。


## 64图三模型实测结果（2026-10-04）

正式结果为 `summary__pilot10_64_three_models_v2_20261004.lance@1`，包含本轮全部固定阶段引用。每个模型均尝试覆盖64个原始SHA；两个源图压缩后产生相同请求图，Qwen原生日志实际63个请求。后续只重放已有响应、重新逐图校验和提交，没有新增模型请求。所有模型仍存在失败，故 summary.complete=False；测试已完成，不能宣称64图全部标注成功。

| 模型/配置 | 有效标注 | 实际请求 | 输入/输出 tokens | 本批首次耗时 |
| --- | ---: | ---: | ---: | --- |
| Qwen3.5-4B，本地、关闭思考、单图、并发8 | 58/64 | 63 | 160,162 / 48,300 | 343.7秒，含加载 |
| malasci/gpt-6.1-sol，xhigh、8图、并发2 | 53/64 | 8 | 51,205 / 36,064 | 进度观测约14分20秒；阶段首次登记已是缓存重放，其7.7秒不作推理耗时 |
| malasci/gpt-6-luna，xhigh、8图、并发2 | 42/64 | 8 | 57,220 / 35,988 | 649.0秒 |

这是本次路由、批大小、并发和GPU配置下的耗时，不是等硬件、等并发的模型推理基准。总tokens按原生journal去重，包含失败调用已报告的usage；不同模型的tokenizer和缓存/计费方式不同，不能直接换算费用。本轮没有可靠价格回执，未估算金额。首版调试Qwen的34次请求另保留在旧run，不在表中。

本次先启动GPT-6.1-sol，用户要求并行后，Luna与Qwen同时提交并与尚在运行的GPT重叠。现役入口支持独立模型锁、分模型提交及只读汇总；没有在行函数中调用其他pipeline。原串行进程在GPT所有8条响应持久化后停止，GPT阶段随后全部从同一journal重放提交。Qwen同图并发产生的一条临时未确定回执，在原请求完成后通过只读重放取回；未清journal或重发未知请求。

**失败分解。** GPT为一批HTTP401影响8图、1图关系指向自身、2图将“昏暗”写成了枚举外可见性问题。Luna为两批JSON额外括号导致16图不可解析，另1图关系类型写成“骑手”、2图对象ID关系无效、3图漏写count。Qwen为1图输出到8192 tokens后截断、1图使用枚举外“骑乘”、3图把无法确认与确定视角混填、1图引用未知对象。原始输出和错误均保留，没有把模型的非法值自动替换成猜测值。

完整JSON只有个别图片字段违反schema时，解析器读取该次固定原生response_ref，对每张图独立校验，保留其余合格项；原始批次错误仍记录。重复、遗漏或错配图片编号依然整批失败；整个JSON语法坏了、HTTP错误或截断不会伪造有效标注。此修正仅重放现有模型输出。

**与GPT-6.1-sol的一致性。** 三模型共同有效的28图使用相同分母：

| 字段（集合字段为完全相等） | Qwen | Luna |
| --- | ---: | ---: |
| 主体组合形式 | 19/28，67.9% | 22/28，78.6% |
| 取景 | 20/28，71.4% | 20/28，71.4% |
| 视角集合 | 10/28，35.7% | 13/28，46.4% |
| 文字是否可见 | 26/28，92.9% | 25/28，89.3% |
| 水印是否可见 | 26/28，92.9% | 28/28，100% |
| 关系类型集合 | 7/28，25.0% | 14/28，50.0% |
| 可见性问题类型集合 | 2/28，7.1% | 12/28，42.9% |

共同28图中，GPT标为“多个不同类对象”的19图，Qwen召回12张（63.2%）、Luna召回15张（78.9%）；这是相对GPT标签的召回，不是人工真值召回。28图中GPT有水印9图，无水印19图，故水印一致率并非全由“未观察到”组成。更大成对可判子集：Qwen与GPT为47图，组合形式31/47（66.0%）；Luna与GPT为33图，组合形式25/33（75.8%）。这些分母经过有效性筛选，不可推广至全300概念或全库。

对象名称自由文本的字面集合一致率很低，包含“男子/工人”“骑马者/骑手”等正常表述差异，故不作为语义质量结论。关系类型集合相等也不证明关系两端和依据一致。详细caption目前只作逐图查看与抽查，没有伪造语义正确率。

**已看实际图片核查的例子。**

- `82a76061d764…` 是骑手与马的比赛照片，Qwen正确列出骑手和马，却把主体组合形式写成“多个同类对象”；GPT写成多个不同类对象。主枚举直接硬过滤会漏掉这类组合素材。
- `d479ea56ab89…` 明确显示棋盘和独立棋子，Qwen列出二者但组合形式仍为多个同类对象；GPT为多个不同类对象。
- `58c20823b4f3…` 是整体LOVE字母图案，Qwen将四个字母拆成不同类对象，GPT按整体图案处理。这里有整体与部件的粒度差异。
- GPT自身也出现批量串图内容：`284c65b842fb…` 是紫边特洛伊绘画，GPT caption 却写入同批 `4290a8b483d3…` 埃及人物图才有的“gettyimages / Credit: duncan1890 / OSIRIS.”文字和水印。两张原图已核看；此GPT行另因关系自指被判失败。不能把GPT批量输出自动当成真值。

原图尺寸由程序读出：64张中11张双边均达到1024，12张最长边不足512。小图自身的可见性限制需要与模型差异一起看，源图数量不等于高分辨率可用量。

**当前结论。** Qwen在此次配置下更快，但组合形式和关系标签尚不适合直接硬过滤，尤其会漏掉实际有多个对象的图片。Luna在共同有效子集上有部分改进，但本次JSON/字段契约失败较多，也不能据此替换为全量标注模型。可先将这些标签用于候选召回与排序；下一轮应先修复结构化输出约束、整体/部件与主要对象的判定边界，再用独立人工核查的小样本验证组合图召回和批看串图风险。没有启动300概念全量标注。

最终验证：本模块4项测试（错图绑定、无效对象ID、真实Dataset/HTTP/缓存/分模型阶段/汇总闭环、保留同批合格标注）通过，CLI/布局/规范引用/登记4项检查通过。日常查看使用本模块四格notebook；第3格同时给成对和共同有效子集，第4格默认展示骑手与马的分歧图，可改索引并查看完整真实请求。
